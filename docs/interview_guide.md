## 0. 一分钟版本（开场白）

> 我写了一个小型 AI Coding Agent，叫 CodeAgent，参考 Claude Code 的架构用 Python 从零实现，4,000 行、168 个测试。
> **核心循环是手写的**——没有用 LangGraph 或 Agent SDK，因为我想搞清楚 agent 的循环、上下文治理、权限这些底层是怎么运作的。
> 我重点解决的是长会话里真正会出问题的地方：上下文怎么不爆、DeepSeek 的缓存怎么持续命中省钱、进程被杀怎么续跑、记忆怎么跨会话生效、以及**改得对不对由谁来判**。
> 最后我给它配了一套真实仓库的评估：从 tinydb 的 git history 里挖真实的 bug 修复提交当题目，用隐藏测试判分，出完成率和成本报告。

**三个可以主动抛出的钩子**（面试官通常会接其中一个）：
1. 「Claude Code 里**只读工具并发、写工具串行**，我照搬了这个语义」→ 引到循环设计
2. 「我用 provider 的实测 usage 做记账，而不是自己估 token」→ 引到上下文治理
3. 「我的评估集不是编的，是从真实仓库的 git history 挖的」→ 引到评估设计

## 1. 为什么手写循环，而不是用 LangGraph？

**答**：这是个刻意的取舍。LangGraph 是很好的编排框架，但它的抽象是「图 + 节点 + 边」，适合**流程确定**的场景（workflow）；coding agent 是**流程不确定**的（agent）——下一步做什么完全由模型决定。套框架我能跑通，但说不清几件事：

- 步数上限、终止判定（什么算完成、什么算原地打转）在哪一层实现？
- 工具并发/串行的语义谁保证？**顺序错了会怎样**？
- 上下文满了怎么压缩？压缩之后缓存还命中吗？
- 进程被杀，进度怎么恢复？

这些恰好是 agent 工程里最容易出问题的地方。手写循环意味着这些全在我的控制之下，每一处都能讲清楚设计和权衡。

> 补充一句得分点：Anthropic 那篇 *Building Effective Agents* 的核心建议就是「**从最简单的开始，别过早套框架**」，并且明确区分 workflow（预定义代码路径）和 agent（模型动态决定）。这个项目的定位就是后者。

**追问：不用框架，那工程上怎么保证不失控？**
三条坍缩防护：`max_steps` 硬上限（默认 25）、**循环检测**（最近 4 步的工具签名集合完全一致就中止）、system prompt 里的硬约束（不许无意义重复、连续失败要停下来报告）。终止原因会写进 `RunResult.terminated_reason`，所以每次运行**可审计**——是正常完成还是撞上限，一目了然。

## 2. 循环设计：只读并发 / 写工具串行

**为什么**：探索阶段（`read`/`grep`/`glob`）的调用互相独立，并发能直接省墙钟时间；写操作必须保序，否则两个 edit 撞同一个文件就是数据竞争。

**怎么做**（一个容易被追问的实现细节）：

```python
if all_read_only and len(calls) > 1:
    with ThreadPoolExecutor(max_workers=min(4, len(calls))) as executor:
        results = list(executor.map(invoke, calls))   # map 保序！
else:
    results = [invoke(call) for call in calls]
```

**这里有个坑值得讲**：用的是 `executor.map` 而不是 `as_completed`。因为 OpenAI 协议要求每条 `tool` 消息的 `tool_call_id` 必须与上一条 assistant 消息的 `tool_calls` 一一对应——**顺序乱了下一轮请求直接 400**。并发只影响执行速度，绝不能影响消息顺序。

**追问：并发安全吗？** 工具本身是无状态的（`ToolContext` 每次调用传入，工具不持有可变状态），且并发的都是只读工具，所以没有共享写。

## 3. 上下文治理（最该重点讲的一节）

### 3.1 记账：为什么不信自己的估算

**答**：token 估算是**必然有偏差**的（按字符数除一个比例，代码/中文/JSON 的密度完全不同）。而 provider 每轮都返回**实测**的 `usage`——不用白不用。

所以我的策略是 **provider-usage-first**：
```
上下文大小 = 最近一次 provider 实测 total_tokens（锚点） + 锚点之后新增消息的估算（尾部）
```
只对「锚点之后」做估算，误差被限制在很小的一段里。

**最关键的细节**：compact 之后这个锚点就**失效**了——压缩前的 usage 度量的已经不是压缩后的上下文了。所以我给 state 打上 `usage_stale_reason` 标记，有标记就退回全量估算。**用旧 usage 度量新上下文**是这类系统里很隐蔽的一个 bug。

### 3.2 两级 compact：先确定性，后 LLM

| 触发线 | 手段 | 成本 |
|---|---|---|
| `utilization ≥ 0.70` | **确定性 snip**：保留最近 12 条（轮次边界对齐），中段删除 + 插入 boundary 标记 | ≈ 0（纯代码） |
| `utilization ≥ 0.85` | **LLM 摘要**：中段压成一条摘要消息 | 一次 LLM 调用 |

**为什么不全用 LLM 摘要**：LLM 摘要更贵、更慢、还可能失败。0.70~0.85 这个区间用零成本的确定性裁剪就够了，只有真的逼近上限才值得上 LLM。而且 **LLM 失败时自动退化为 snip**（`except Exception: return self._snip(...)`）——压缩失败绝不能让任务挂掉。

**裁掉的消息丢了吗？** 没有。完整内容在 `data/sessions/{sid}.jsonl` 的轨迹里（append-only），snip/summary 标记都指向那里。所以检查点回放看到的是 compact 前的完整对话。

### 3.3 cache-aware 布局（差异化亮点）

**这是我最想讲的设计**。DeepSeek 的上下文磁盘缓存是**按前缀匹配**的：前缀只要有一点变化，后面全部 miss（未命中 ¥2/M vs 命中 ¥0.5/M，**4 倍价差**）。

所以我的消息布局约定：**`system` + 首条 `user` 任务恒定占前两位**（`_PREFIX_LEN = 2`），compact **只动中段，绝不触碰前缀**。这样随着会话推进，前缀一直不变，缓存持续命中，命中率曲线是上升的。

控制台实时画这条曲线，并按公开定价估算省了多少钱——**这是能看到钱的优化**，不是纸面上的。

**追问：为什么前缀稳定就能命中？** 因为 KV cache 是按 token 前缀做的，前缀 token 序列不变，这部分的 KV 就能复用。任何插在前面的变化（包括往 system 里塞新内容）都会导致整条前缀失效。

## 4. 检查点与崩溃恢复

**做什么**：每 5 步把整个 `AgentState`（messages + usage + events）原子落盘到 `data/checkpoints/{sid}/step-{N}.json`。

**两个细节会被追问**：

1. **原子写**：先写 `.json.tmp` 再 `replace()`。**进程被 kill 时绝不会留下半个 JSON**——否则 resume 时读到损坏的检查点，比没有检查点更糟。
2. **续跑不重置 step 计数**：恢复出来的 `state.step` 继续往上加，所以续跑产生的检查点**不会覆盖**恢复前的同名文件，轨迹里也没有歧义。

**和「会话恢复」的区别**（如果面试官熟悉 Claude Code）：Claude Code 的 `/resume` 是**会话级**恢复；我做的是**step 级**检查点，所以能演示「任务跑到一半 kill -9，再 `--resume` 接着跑完」。

## 5. 权限与 hooks

**权限**：三类请求（path / command / edit），决策粒度六级——`allow_once` / `allow_turn` / `allow_always` / `deny_once` / `deny_always` / `ask`。为什么不做简单的 allow/deny/ask 三态？因为实际用起来，「每次都问」会很烦，「一次全允许」又太危险，**「本回合内允许」**才是真正好用的粒度。控制台的权限确认就是五个按钮。

**hooks**：`PreToolUse` / `PostToolUse`。内置的 block-at-submit 示例：`git commit` 前检查 `data/tests_pass.marker` 是否存在，不存在就**阻断**，并把「先去跑 pytest」回喂给模型，逼它进入「测试 → 修复 → 再提交」的循环。

**这里有个认知值得讲**：钩子是**确定性的「必须做」**，而 CLAUDE.md（记忆文件）是**建议性的「应该做」**。想让 agent 一定遵守某条规则，写在提示词里是不可靠的——**用代码拦它**。这是 agent 工程里「确定性约束 > 提示词祈祷」的具体体现。

**追问：hook 阻断了模型会不会卡死？** 不会。阻断信息是作为工具结果**回喂给模型**的（不是抛异常终止），模型看到「先跑测试」的提示后会自己去跑测试。

## 6. 记忆（分层 + 自进化）

**分层**（低 → 高优先级）：`CODEAGENT.md` < `MINI.md` < `CLAUDE.md` < `.codeagent/rules/*.md`（`learned.md` 排最后 = 最高优先级）。逻辑是：**离当前工作区越近的知识越该被信任**。

**@include**：`@相对路径` 递归原位展开。安全边界值得讲：只接受相对路径，**显式拒绝绝对路径、`..` 段（含 `sub/../x` 这种伪装）、沙箱逃逸**；循环 include 用 seen 集合检测；文件缺失给占位注释而不是报错——**记忆文件坏了不该让整个任务崩掉**。

**去重 + 预算**：内容 sha256 去重（重复时保留靠后=高优先级那份）；单文件 8K、总计 20K 预算，超了截断并**明确提示**。

**自进化（这条最有意思）**：任务结束后从轨迹里提炼约定（`extract_conventions`）→ `consolidate`（归一化 + 子串包含合并 + hash 去重）→ 写回 `learned.md` → **下次 `discover` 自动包含**。所以约定**跨会话生效**。参考实现里 MiniCode 只有「加载记忆」没有「写回记忆」，这是我认为该补上的一环——**记忆不进化就只是配置**。

## 7. research 子代理（上下文经济学）

**理论依据**（飞书那篇 CC 分析里的原话）：一个复杂任务需要输入 X、过程累积 Y、产出结论 Z。跑 N 个，主上下文累积 `(X+Y+Z)×N`；SubAgent 把 `(X+Y)×N` 外包，**主上下文只收 Z**。

**实现要点**：
- **独立上下文**：子代理有自己的 `AgentState`，与主循环的 messages / usage / compact 完全隔离；
- **受限只读**：白名单只给 `glob` / `grep` / `read`；`_restricted_registry` **永不包含 subagent 自身** → 从结构上禁止无限递归（比运行时判断"深度<3"更可靠）；
- **复用循环**：内部直接跑同一个 `QueryEngine`，不复制代码；
- **失败如实**：超步或异常返回 `ToolResult.fail("[子代理 max_steps，N 步] …")`，**不假装成功**，主模型据此决定自己上手。

**追问：子代理会不会失控？** 三道闸：只读工具白名单、`max_steps=10`、无 subagent 工具（禁递归）。子代理**不能改任何文件**——所有修改必须由主循环完成，这也是 Claude Code coordinator 模式的原则（worker 只读，root 负责写）。

## 8. 评估（最容易被追问的一节）

**为什么评估重要**：agent 项目最容易自嗨——demo 跑通一个例子就说"能用"。但**改得对不对必须有客观判定**。

**我的评估集怎么来的**（这条一定要讲清楚，是加分项）：读 tinydb 的真实 git history，筛出「subject 含 fix 关键字 **且**同时改了源码和 tests」的提交，然后：

| 要素 | 取值 | 为什么 |
|---|---|---|
| 任务描述 | 该提交的 subject + body | **真实的 bug 报告**（当时开发者自己写的），不重写成谜语 |
| 起始状态 | 该提交的**父提交** | bug 确实存在的状态 |
| 判分依据 | 该提交里 `tests/` 的内容 | **隐藏测试**，agent 全程看不到 |

**这绕开了 SWE-bench 类任务的两个经典陷阱**：
1. **测试泄漏**——判定用的测试如果 agent 能读到，就是开卷考试。这里隐藏测试只在 judge 阶段写回。
2. **任务描述失真**——把真实 bug 改写成谜语，会让任务变得不可解（连人都不确定要什么）。

**工程细节**：`git worktree add --detach` 给每个任务独立工作区（不污染主仓库），跑完 `remove_worktree` 清理；成本按 DeepSeek 公开定价 + **实测 usage** 估算；**agent 异常或 judge 异常如实写进报告的 `error` 字段**。

**被追问「完成率多少」时怎么答**（诚实很重要）：
> 真实跑分需要 API key，我不想编一个数字给你。**mock 冒烟下完成率是 0%——这是正确的判定结果**，因为 mock 模型根本不修 bug，它验证的是管线连通性。报告里的数字要么是实测的，要么标注为待跑。

## 9. 工具系统

**协议**：`name` / `description` / `Input`（pydantic v2 model，自动生成 JSON Schema）/ `execute` / `is_read_only()`。用 pydantic 对齐 Claude Code 的 zod `inputSchema`。

**两个设计细节**：

1. **参数扁平化**：工具参数不用嵌套结构，避免生成的 schema 出现 `$defs` 引用。**有些模型的 function calling 对 `$ref` 支持不好**，扁平化是最省事的兼容手段。
2. **edit 的唯一匹配语义**：匹配到 0 处或 >1 处都判定失败，并把原因（以及 diff 上下文）回喂给模型。这样模型能自己修正——比「模糊替换」安全得多（模糊替换会改错地方，而且**静默**）。

**截断必须可感知**：`glob`/`grep` 结果截断时，返回里明确告诉模型「还有更多，用更精确的模式」。**静默截断是最危险的**——模型会以为它看到了全部，然后基于不完整信息做决策。

## 10. 可能的压力问题与回答

**Q：你这不就是把 Claude Code 抄了一遍吗？**
> 架构是参考，实现和取舍是我自己的。而且有几个地方我是**明确做了不同选择**的：cache-aware 布局 + 缓存省钱指标（Claude Code 没有面向 DeepSeek 缓存做布局优化）、step 级检查点（它是会话级 resume）、轨迹驱动评估（它没有内置评估）、记忆自进化写回。这些都在 architecture.md 的映射表里逐条标了差异。

**Q：为什么不用向量 RAG 做代码检索？**
> 因为**代码检索用精确匹配比向量更准**——Claude Code 自己就是 grep/glob/read。函数名、变量名是精确符号，不是语义相近的自然语言。加一层向量库会引入 embedding 成本、索引维护、召回不准三个问题，收益却不如一个写好的 grep。

**Q：如果上下文还是爆了怎么办？**
> 三层防线：0.70 确定性裁剪 → 0.85 LLM 摘要 → 超大工具结果**落盘**只留预览+路径（不丢信息）。加上 `max_steps` 硬上限，最坏情况是任务中止并如实报告，**不会无限烧 token**。

**Q：怎么保证 agent 不假装完成？**
> system prompt 里明确要求「不要假装完成，必须实际验证，验证失败要报告」；更硬的保障是结构性的——评估时用**隐藏测试**判分，它说完成了但测试没过，就是 0 分。**判断权不在模型手里**。

**Q：你怎么知道你的某个改动真的有效？有没有过"改了但没效果"的情况？**
> 有过，而且我把它记在 TASKS.md 里了。真实模型验证时我遇到 agent 猜 `/workspace`、遍历磁盘找路径的情况，就往 system prompt 里注入了工作目录，commit message 写的是「修 `--resume` 迷路的真根因」。
> 后来我用**同一任务、同一仓库、只换 system prompt** 做了 A/B（新旧 prompt 各跑一遍，扫描轨迹里的「瞎猜路径」模式），结果是：**步数没有差别**（6 步 vs 6 步，两边都修好、两边都没瞎猜），`--resume` 续跑场景也**没有差别**（都续跑 3 步）。
> 我没改历史，而是追加了一条更正：这次改动如实定性为**防御性健壮性改进**，而不是"修掉了一个 bug、步数下降"。
> 但实验也捞到了一个**真的差异**：我加了一个机制探针（任务是"把工作目录的绝对路径写进文件"），新 prompt 写**对**，旧 prompt 写**错**。顺着这个差异查下去，发现根因是 Windows 上 `pwd` 被 Git for Windows 的 `pwd.exe` 抢占，返回 `/d/RAG项目/...` 这种 **POSIX 路径**——在这台机器上根本不是合法路径，而 `cd`（不带参数）返回的才是 `D:\RAG项目\...`。于是把「确认当前目录用 `cd`，不要用 `pwd`」补进平台提示。
> 我的体会是：**"改动有道理"和"改动有收益"是两件事**，只有 A/B 能把它们分开；而 A/B 跑出来没差别时，正确的做法是更正口径，不是换个指标继续声称。

**Q：这个项目最大的技术难点是什么？**
> 上下文治理里的**记账准确性**。一开始我按消息全量估算 token，但估算偏差会累积，导致 compact 触发时机完全不对——要么该压不压（爆上下文），要么过早压（白丢信息）。改成 provider 实测值做锚点、只估尾部之后，触发时机才稳定。另一个坑是 compact 后忘了把旧 usage 标 stale，结果用压缩前的 usage 度量压缩后的上下文，utilization 直接算错。

**Q：下一步会做什么？**
> 三个方向：
> ① **MCP 的 HTTP/SSE 传输**——现在只做了 stdio（本地 server），远端 MCP server 走 HTTP，协议层可复用，只换传输；
> ② **子代理并发**——现在 research 子代理是单发的，可以做成最多 3 个并发（各自独立上下文），适合「同时调研 3 个模块」这类任务；
> ③ **评估集扩容**——现在只跑 tinydb 一个仓库，接更多仓库能让完成率更有统计意义。

## 11. MCP 客户端（工具生态）

**做了什么**：手写了一个最小 MCP 客户端，能把标准 MCP server 的工具接进来当普通工具用。

**为什么手写而不用官方 `mcp` SDK**（这题一定会被问）：
> ① 官方 SDK 是 **async**（anyio）的，而我的 QueryEngine 是**同步**循环——为了一个工具把整条循环改成 async 不划算，同步版本阻抗最小；
> ② MCP 的 stdio 传输就是「JSON-RPC 2.0 按行分隔」，协议面很窄（`initialize` / `tools/list` / `tools/call`），手写一遍比封一层 SDK 更透明；
> ③ 不引入新依赖。

**一个真实的工程坑**：读管道**没法设超时**（Windows 上 `select` 也不支持 pipe）。我的解法是给 stdout/stderr 各起一个后台线程持续抽干：stdout 抽到队列里，请求按 `id` 去队列里取（`queue.get(timeout=...)` 天然支持超时）；stderr 抽到环形缓冲——这样出错时能把 **server 自己的报错**带进异常信息，而不是干巴巴一句"超时"。

**安全边界（这是我认为最该讲的一点）**：MCP 工具来自第三方 server，**不受我的 workspace 沙箱约束**。所以：
1. **必须显式配置才注册**（`--mcp`），不进默认工具集；
2. 只读性**只信 server 声明的 `annotations.readOnlyHint`**，没声明就当可写 → 串行执行，绝不并发跑未知副作用；
3. **它们照样走 `_gate_and_run` 门禁链**——权限引擎和 hooks 对 MCP 工具同样生效；
4. **权限默认不放行**：`allow` 里列出来的工具才免确认，其余判定 `ask`（CLI 无交互确认 → 拒绝）。

第 3 点是**分层设计的回报**：接入一个全新的工具来源，循环一行都不用改。如果权限和 hooks 是写死在循环里的，这里就得动核心代码。

**但第 3 点同时是我踩过的坑，也是我更愿意讲的一段**：能走门禁**不等于**门禁有正确的策略。MCP 工具名落到权限引擎里走的是通用 `tool` 分类，而那条路的兜底是 `return ALLOW` —— 于是「接上第三方 server 就默认信任」，第 3 点的分层回报在这里变成了分层的盲区。修法是给 `Tool` 加 `is_external()`，`_classify` 把外部工具单独归一类，`_rule_check` 里 `external` 分支命中白名单才 `ALLOW`、否则 `ASK`。**这一条我是在做注入防御时回头审自己的代码才发现的**：加一个安全特性的时候，顺手审出了三个别的洞（还包括子进程继承 `DEEPSEEK_API_KEY` 环境变量、`run_post` 的返回值被丢弃导致 PostToolUse 那层治理从未到达模型）。我把它们和误报修复一起单独成 commit，没有混进新特性里。

顺带一个设计细节：`allow` 的匹配放在 `load_mcp_servers` 里做，而不是权限引擎里 —— 因为只有那一处同时知道「远端工具名」和「注册名」（与内置工具重名时会加 `<别名>__` 前缀）。否则用户得去猜前缀，配置就成了实现细节的泄漏。

**测试怎么做**：写了一个**真实的假 MCP server**（`tests/fake_mcp_server.py`）——真子进程、真管道、真 JSON-RPC 往返。所以测试能覆盖握手、跨进程读超时、server 中途崩溃这些**只有真进程才会暴露**的问题。还有一个测试让 MCP 工具**经真实 QueryEngine 循环**被调用，验证集成而不只是协议。权限侧另有一组：外部工具默认 `ASK`、授权后 `ALLOW`、拒绝文案里必须含 `mcp.json` 与工具名（拒绝而不说怎么解，只会让 agent 反复重试同一个调用）。

## 12. 现场演示动线（5 分钟）

1. **无 key 演示**（30 秒）：`python -m app.cli --mock "读 README 并总结项目结构"` — 真实执行 glob，Mock 给结论
2. **危险命令拦截**（30 秒）：让 agent 跑 `rm -rf /`。**说清是哪一层拦的**：不是 bash 工具自己拒绝，而是权限引擎判定 `ask`，CLI 无交互确认 → loop 按安全默认拒绝，理由回喂模型让它改道。bash 工具里的模式匹配只是**没有权限引擎在场时**的兜底（`ctx.permissions is None` 那条分支）——两条路都存在，但默认走的是权限引擎那条。
3. **block-at-submit**（1 分钟）：让 agent 提交代码，看 hook 因测试未通过而阻断
4. **崩溃恢复**（1.5 分钟）：跑长任务 → 中途 `Ctrl+C` → `--resume` 接着跑完，展示检查点文件
5. **控制台**（1.5 分钟）：`streamlit run app/ui_streamlit.py` — 缓存命中率曲线 + 省钱估算 + 检查点回放
6. **评估**（可选）：`python -m eval.runner --limit 2 --mock` — 展示报告的诚实判定（0% = mock 真没修 bug）
7. **MCP 与第三方工具授权**（可选）：`python -m app.cli --mock --mcp .codeagent/mcp.json "任务"` — 看第三方工具被注册进工具集、走同一套门禁，且**没列进 `allow` 的工具被拒绝**（拒绝文案里带出处和解除方式）。这段可以顺带讲「能走门禁 ≠ 门禁有正确策略」，是第 11 节那个坑的现场版。

## 0. 一分钟版本（开场白）

> 我写了一个小型 AI Coding Agent，叫 CodeAgent，参考 Claude Code 的架构用 Python 从零实现，12,568 行、707 个测试。
> **核心循环是手写的**——没有用 LangGraph 或 Agent SDK，因为我想搞清楚 agent 的循环、上下文治理、权限这些底层是怎么运作的。
> 我重点解决的是长会话里真正会出问题的地方：上下文怎么不爆、DeepSeek 的缓存怎么持续命中省钱、进程被杀怎么续跑、记忆怎么跨会话生效、以及**改得对不对由谁来判**。
> 最后我给它配了一套真实仓库的评估：从 tinydb 的 git history 里挖真实的 bug 修复提交当题目，用隐藏测试判分，出完成率和成本报告。

**三个可以主动抛出的钩子**（面试官通常会接其中一个）：
1. 「Claude Code 里**只读工具并发、写工具串行**，我照搬了这个语义」→ 引到循环设计
2. 「我用 provider 的实测 usage 做记账，而不是自己估 token」→ 引到上下文治理
3. 「我的评估集不是编的，是从真实仓库的 git history 挖的」→ 引到评估设计

## 1. 为什么手写循环，而不是用 LangGraph？

**答**：这是个刻意的取舍。LangGraph 是很好的编排框架，但它的抽象是「图 + 节点 + 边」，适合**流程确定**的场景（workflow）；coding agent 是**流程不确定**的（agent）——下一步做什么完全由模型决定。套框架我能跑通，但说不清几件事：

- 步数上限、终止判定（什么算完成、什么算原地打转）在哪一层实现？
- 工具并发/串行的语义谁保证？**顺序错了会怎样**？
- 上下文满了怎么压缩？压缩之后缓存还命中吗？
- 进程被杀，进度怎么恢复？

这些恰好是 agent 工程里最容易出问题的地方。手写循环意味着这些全在我的控制之下，每一处都能讲清楚设计和权衡。

> 补充一句得分点：Anthropic 那篇 *Building Effective Agents* 的核心建议就是「**从最简单的开始，别过早套框架**」，并且明确区分 workflow（预定义代码路径）和 agent（模型动态决定）。这个项目的定位就是后者。

**追问：不用框架，那工程上怎么保证不失控？**
三条坍缩防护：`max_steps` 硬上限（默认 25）、**循环检测**（最近 4 步的工具签名集合完全一致就中止）、system prompt 里的硬约束（不许无意义重复、连续失败要停下来报告）。终止原因会写进 `RunResult.terminated_reason`，所以每次运行**可审计**——是正常完成还是撞上限，一目了然。

## 2. 循环设计：只读并发 / 写工具串行

**为什么**：探索阶段（`read`/`grep`/`glob`）的调用互相独立，并发能直接省墙钟时间；写操作必须保序，否则两个 edit 撞同一个文件就是数据竞争。

**怎么做**（一个容易被追问的实现细节）：

```python
if all_read_only and len(calls) > 1:
    with ThreadPoolExecutor(max_workers=min(4, len(calls))) as executor:
        results = list(executor.map(invoke, calls))   # map 保序！
else:
    results = [invoke(call) for call in calls]
```

**这里有个坑值得讲**：用的是 `executor.map` 而不是 `as_completed`。因为 OpenAI 协议要求每条 `tool` 消息的 `tool_call_id` 必须与上一条 assistant 消息的 `tool_calls` 一一对应——**顺序乱了下一轮请求直接 400**。并发只影响执行速度，绝不能影响消息顺序。

**追问：并发安全吗？** 工具本身是无状态的（`ToolContext` 每次调用传入，工具不持有可变状态），且并发的都是只读工具，所以没有共享写。

## 3. 上下文治理（最该重点讲的一节）

### 3.1 记账：为什么不信自己的估算

**答**：token 估算是**必然有偏差**的（按字符数除一个比例，代码/中文/JSON 的密度完全不同）。而 provider 每轮都返回**实测**的 `usage`——不用白不用。

所以我的策略是 **provider-usage-first**：
```
上下文大小 = 最近一次 provider 实测 total_tokens（锚点） + 锚点之后新增消息的估算（尾部）
```
只对「锚点之后」做估算，误差被限制在很小的一段里。

**最关键的细节**：compact 之后这个锚点就**失效**了——压缩前的 usage 度量的已经不是压缩后的上下文了。所以我给 state 打上 `usage_stale_reason` 标记，有标记就退回全量估算。**用旧 usage 度量新上下文**是这类系统里很隐蔽的一个 bug。

### 3.2 三级 compact：先缩内容，再删消息，最后才花钱调 LLM

| 触发线 | 手段 | 成本 |
|---|---|---|
| `utilization ≥ 0.70` | **第 0 级 · 分级截断**：按工具给预算把**工具结果的正文**缩短（`read` 4K / `grep` 3K / `glob` 2K / `bash` 6K，**失败结果 16K**），head 70% + tail 30%，**不删消息** | ≈ 0（纯代码） |
| 第 0 级缩完仍 `≥ 0.70` | **第 1 级 · 确定性 snip**：保留最近 12 条（轮次边界对齐），中段删除 + 插入 boundary 标记 | ≈ 0（纯代码） |
| `utilization ≥ 0.85` | **第 2 级 · LLM 摘要**：中段压成一条摘要消息 | 一次 LLM 调用 |

**为什么不全用 LLM 摘要**：LLM 摘要更贵、更慢、还可能失败。0.70 起的区间先用零成本的两级就够，只有真的逼近上限才值得上 LLM。而且 **LLM 失败时自动退化为 snip**（`except Exception: return self._snip(...)`）——压缩失败绝不能让任务挂掉。

**为什么第 0 级排在最前**：它**不删消息**，所以 `tool_call_id` 配对天然完整，不存在 snip 要处理的那两类孤儿边界问题；而且它保住了「模型还能看到结论」这件事。两个细节值得主动说：

- **head 70% + tail 30%**，不是只留头部 —— `grep`/`pytest` 的**结论在尾部**（失败摘要、总计行），只留头等于把最该看的部分丢掉。
- **失败结果给更大预算**（16K vs 4K）—— 错误原文是模型自修复的唯一依据，这是项目「失败一律文本回喂」原则在上下文层的延续。

**第 0 级有一条不变量，值得单独讲**：**只在越过 0.70 时才跑**。低于阈值必须**逐字节不碰**，否则每个大工具结果在其生命周期内至少破坏一次前缀缓存。这条约束的特殊之处是——**破坏它是静默的**：没有报错、没有测试变红，只有一条走平的命中曲线和更贵的账单。所以专门写了一条「utilization < 0.70 时消息逐字节不变」的测试盯着它。

**但这条机制我也做了实测，结论对设计不利，照样讲**（2026-09-11，DeepSeek 官方通路，两个压力区间 + 一次微观对照）：

- **端到端命中率没降**：两臂只差这一个开关，B−A 都在 ±0.02% 以内（一个区间两臂的累计 hit token 逐 token 相同）。所以「不变量守住了」这句是**测出来的**，不是设计推理。
- **但代价不是零，只是被遮蔽了**：截断触发的那一步，第 2 级 LLM 摘要**也在同一步触发**，缓存本来就整段失效。把一次截断单独拎出来对照，它省 5,128 token、付 **45,304 miss token（8.8 倍）**，该步命中率 100% → 28%。
- **代价的形状是后缀失效**：由 head 70% 决定，前缀缓存匹配到那 70% 处才分叉，**被改的那条之后全算未命中**。所以代价取决于"它后面还压着多少"——同样截 4,000 字符，截第 7 条（后面 12 条）少命中 50,432，截第 17 条（后面 2 条）只少 13,312，差 3.8 倍。它是一次性的（重发一次就回到基准）。
- **它也没能免掉下一级**：中段窗口要到 20 条消息才非空，那时 utilization 已经 1.06~1.23，远在 0.85 之上。一次释放的 token 只值预算的 5.9~7.4 个百分点，每步增量 11~13 个百分点——**追不上**。

> 这段的价值在于它是个**「设计对了、收益比预期小」的诚实样本**：如果只讲第一层（命中率没降），听起来是成功的优化；把三层连起来看，真实结论是"不变量该守，但这条机制的收益要重新评估"。我已经把三个选项（保持 / 改成优先截最靠后的合格消息，缓存代价降到 1/3.8 / 直接去掉）连同数据写进 TASKS.md，**没有单方面改设计**——因为"截最老的还是最新的"背后是一个相关性取舍，不只是缓存算术。

**裁掉的消息丢了吗？** 没有。完整内容在 `data/sessions/{sid}.jsonl` 的轨迹里（append-only），snip/summary 标记都指向那里。所以检查点回放看到的是 compact 前的完整对话。

### 3.3 cache-aware 布局（差异化亮点）

**这是我最想讲的设计**。DeepSeek 的上下文磁盘缓存是**按前缀匹配**的：前缀只要有一点变化，后面全部 miss（未命中 ¥2/M vs 命中 ¥0.5/M，**4 倍价差**）。

所以我的消息布局约定：**`system` + 首条 `user` 任务恒定占前两位**（`_PREFIX_LEN = 2`），compact **只动中段，绝不触碰前缀**。这样随着会话推进，前缀一直不变，缓存持续命中，命中率曲线是上升的。

控制台实时画这条曲线，并按公开定价估算省了多少钱——**这是能看到钱的优化**，不是纸面上的。

**追问：为什么前缀稳定就能命中？** 因为 KV cache 是按 token 前缀做的，前缀 token 序列不变，这部分的 KV 就能复用。任何插在前面的变化（包括往 system 里塞新内容）都会导致整条前缀失效。

## 4. 检查点与崩溃恢复

**做什么**：每 5 步把整个 `AgentState`（messages + usage + events）原子落盘到 `data/checkpoints/{sid}/step-{N}.json`。

**两个细节会被追问**：

1. **原子写**：先写 `.json.tmp` 再 `replace()`。**进程被 kill 时绝不会留下半个 JSON**——否则 resume 时读到损坏的检查点，比没有检查点更糟。
2. **续跑不重置 step 计数**：恢复出来的 `state.step` 继续往上加，所以续跑产生的检查点**不会覆盖**恢复前的同名文件，轨迹里也没有歧义。

**和「会话恢复」的区别**（如果面试官熟悉 Claude Code）：Claude Code 的 `/resume` 是**会话级**恢复；我做的是**step 级**检查点，所以能演示「任务跑到一半 kill -9，再 `--resume` 接着跑完」。

**step 级检查点还白送一个能力：分叉（M9-3）**。`--fork --step K` 从任意一步另开一条路，而 TS 原版的 `/fork` 是**会话级**的（整段复制、从"现在"接着走）—— 这不是我多写了多少代码，是**检查点粒度的直接推论**，这一条讲出来比讲实现本身更有说服力。

```bash
python -m app.cli --sessions                              # 名字 / 步数 / 分叉来源（无 key）
python -m app.cli --rename "基线方案"                       # 起名（只动元数据）
python -m app.cli --fork --step 3 "换个思路"                # 从第 3 步分叉并续跑
python -m app.cli --resume --session-id "基线方案" "接着改"   # id **或名字**都能指会话
```

**这里有一条必须主动说的边界**：**单独**用它时，它是**对话分叉，不是工作区分叉** —— 文件**不会**回滚到第 K 步的样子，分叉后的 agent 看到的是**当前**工作区。要让文件也回去，就在**同一个 K** 上加 `--rewind`（M9-8）：`--fork --step 3 --rewind` 才是完整的"倒带重试"。CLI 分叉后把这句打印出来、`--fork` 的 help 也写明。**不说这句，"回到第 3 步"几乎必然被理解成文件也回去了** —— 一句会让人误判的提示比没有提示更糟。

> **而这句话本身必须跟着 `--rewind` 分叉写**：`--fork` 的提示有两句，按**有没有 `--rewind`** 选一句 —— 不带 `--rewind` 时说"文件不会回滚"，带 `--rewind` 时说"文件已回到第 K 步"。这正是本项目头号缺陷类（**接线漂移**）的形状：一句写在五处、只在一条路径上成立的话，加了新出口之后它就开始骗人。M9-8 之前五处文档都写着"我们没有工作区快照机制"，现在那句话只在**不带 `--rewind`** 时成立。

> 三个实现细节，被追问时用得上：
> ① **轨迹不能整份复制**，只搬 `step <= K` 的行 —— 轨迹是追加的，整份搬会让分叉会话"继承"源会话在 K 之后才发生的 `security_finding`（它根本没经历过那些事）。
> ② **副本里唯一按新会话重写的是 `session_id`**。今天 `load_state` 会 pop 掉它所以无害，但谁哪天直接读 `payload["session_id"]` 就会拿到源会话 —— 属"当前无人读、将来必有人读"的错值，在写入时修掉比留着便宜。
> ③ **名字的两条判据合起来才成立**：写入侧拒绝「与任何已有 session_id 或会话名相同」，读取侧**先当 id 再当名字**。少了写入侧的拒绝，重名会让 `--resume --session-id <名字>` **安静地跑到另一个会话上**（带着另一个任务的上下文）—— 所以不在读取侧加优先级去"猜"，猜错的代价太大。
> ④ **`--step K` 里的 K 可能压根没落盘**（检查点按节拍落，`--checkpoint-every 2` 的会话只有偶数步）。这时报的是 `第 3 步没有检查点（可用: [2, 4]）`，不是一个裸文件路径 —— 报错必须给出下一步，而分叉与续跑共用同一个读取入口，一条守卫管住两条路。**抛出侧只是一半**：三条入口（`--resume`/`--fork`/`--plan`）各自要接住它 —— 真实跑发现只有最常用的 `--resume` 漏了，用户拿到一整个 traceback；`--fork`/`--plan` 早就各有一句人话。**同一个错误在三条路径上有三种表现，正是"两处各写一遍"的典型形状。**

**这段我踩过一个两层套娃的坑，很值得讲**（都是真跑挖出来的，不是单测挖的，而单测当时全绿）：

1. `--resume --checkpoint-every 1` **传了不生效**：`--resume` 那条路径没把参数转发下去，回落成默认的 5。现场是 kill 在 step 5（检查点 1..5），续跑到 step 9，结束时的检查点数**还是 5** —— 4 步工作全在内存里，再崩一次整段丢。
2. 修完第 1 条之后（2026-09-11 用户拍板）我又发现**它还有另一半**：不传 `--checkpoint-every` 时回落 CLI 默认值 —— 而**5 是 CLI 的默认值，不是这个会话的事实**。会话当初按 1 步一存起的，恢复后按 5 走。这一半更难发现，因为 **5 凑巧也是个合法节拍**：命令成功、输出正常、退出码 0，唯一证据是检查点数不涨。修法是把节拍**随检查点落盘**，恢复时优先序为「显式传参 > 会话里记的 > 默认」，并且把**实际生效的节拍打印出来** —— 一个静默的默认值，至少要让它在屏幕上可见。

> 我特意提这条是因为它暴露了一个反复出现的缺陷类：**机制在、测试绿、真跑才发现没生效**。测试和判据是同一个脑子写的，会共享盲区。顺带一提，修第 2 条时我还发现**原测试自己在骗自己**：它第一段用的就是 `--checkpoint-every 1`，而这正是会话会记住的值，于是"显式传参没被转发"会因为沿用了会话里那个同样是 1 的值而假装通过。改成第一段用 2、显式传 1，两条路才分得开（未改代码时变异结果的签名是 `[2, 4]` 而不是 `[2,3,4,5]`）。

## 5. 权限与 hooks

**权限**：三类请求（path / command / edit），决策粒度六级——`allow_once` / `allow_turn` / `allow_always` / `deny_once` / `deny_always` / `ask`。为什么不做简单的 allow/deny/ask 三态？因为实际用起来，「每次都问」会很烦，「一次全允许」又太危险，**「本回合内允许」**才是真正好用的粒度。控制台的权限确认就是五个按钮。

**hooks**：`PreToolUse` / `PostToolUse`。内置的 block-at-submit 示例：`git commit` 前检查 `data/tests_pass.marker` 是否存在，不存在就**阻断**，并把「先去跑 pytest」回喂给模型，逼它进入「测试 → 修复 → 再提交」的循环。

**这里有个认知值得讲**：钩子是**确定性的「必须做」**，而 CLAUDE.md（记忆文件）是**建议性的「应该做」**。想让 agent 一定遵守某条规则，写在提示词里是不可靠的——**用代码拦它**。这是 agent 工程里「确定性约束 > 提示词祈祷」的具体体现。

**追问：hook 阻断了模型会不会卡死？** 不会。阻断信息是作为工具结果**回喂给模型**的（不是抛异常终止），模型看到「先跑测试」的提示后会自己去跑测试。

**权限确认带 diff（M9-1）**：`edit` / `write` 在**写盘之前**由 `Tool.preview()` 产出一份 diff，交给权限确认 —— 权限从「事后报告」变成「事前审批」。这里有两个值得讲的点：

- **为什么 diff 由工具算，而不是权限引擎拿 `arguments` 自己算**：`edit` 的「唯一匹配」语义属于工具。引擎重算一遍就有了**两个真相源**，迟早出现「预览说能改、执行说匹配不唯一」——而那时**人已经照着预览点过允许了**。所以 `EditTool._plan` 同时供 `preview` 和 `execute` 用，匹配/计数/替换只写一份。
- **两种失败姿态是相反的**：预览是**信息** → 实现方抛异常就记一条 `preview_failed` 事件并退回原确认框（fail-open）；权限是**判定** → 算不出来必须大声失败（fail-closed）。另外**没有权限引擎时根本不计算预览**：headless 没人能看，而 `edit` 的预览要把整个文件读进来做 diff，算了是白花的每步开销。
- 给人看的 diff 上限 4,000 字符，给模型的仍是 500,000：**几万字符的 diff 会把人逼成"闭眼点允许"，而一个训练用户不看内容的确认框等于没有确认框。**

> **要主动交代边界**：默认配置下这个 diff **到不了人眼前**（`edit` 默认 `allow`、CLI 无确认交互）。它只在三条路出现 —— CLI 的 `--review-edits`、污染天花板收紧、或显式规则把工具抬成 `ask`。TS 参考实现的 edit 是默认要批准的（靠 TTY 模式兜住），我们把默认值留在 `allow` 是因为**没有确认回调时 `ask` 等于拒绝**，那会让 CLI 每次改动都失败。

### 5.1 安全机制：三层，其中只有两层是确定性的（M7）

这是简历上「权限与安全审查 / AI 风险分类」那条的落点，也是最容易被追问的一节。**先把范围说死**：这个项目**没有**做 prompt 注入防御——注入防不住，攻击者改写一个词就绕过。做的是两件分开的事：

| 层 | 模块 | 性质 | 能做什么 |
|---|---|---|---|
| **执行** | `permissions.py` | **确定性**（查表） | 路径沙箱硬 deny · 危险命令 ask · 第三方工具默认 ask · **污染天花板** |
| **阻断** | `hooks.py` PreToolUse | **确定性**（条件判断） | block-at-submit：测试未通过不许 commit |
| **检测** | `security.py` | **概率性**（文本匹配） | 只出告警 + 抬会话污染标记，**从不直接决定放行/拒绝** |

**为什么要分成三层，而不是写成一个扫描器**：因为后两层里只有一层能做判断。文本匹配改一个词就绕过，把它放进执行路径，等于把可靠性建立在猜测上——而这个项目写在 README 第 0 节的原则是「**可靠性来自运行时的确定性，而不是提示词的祈祷**」。所以分界线划在「谁在做判断」上：左边那半靠猜，只能影响告警；右边那半靠查表（标记级别 + 动作类别，两个可判定的量），才能进执行路径。

**污染天花板的位置是这一层最要紧的坐标**。检测到可疑文本后，真正收紧能力的动作是：`high` 会话下，把三类**不可逆**动作从 `ALLOW` 降到 `ASK`。它必须插在决策链的**记忆之后、人工确认之前**：

```
1) 路径越界 → 硬 deny
2) 常驻记忆 _always   ┐
3) 本回合记忆 _turn   ├─ 用户的选择在这里
4) 规则判定 _rule_check ┘
5) 后置天花板  ← 必须在这里
6) ask → confirm()   ← 人的当场决定
```

- **写在 4) 里面是无效的**：会被 2)/3) 短路。用户只要开过一次 `allow_always`，任何基于规则的收紧就**永久失效**——而「记得越久越省事」正是用户去开它的原因，两个方向正好相反。这是我第一版设计里真实踩到的坑（评审时逐行读代码才发现）。
- **放在 6) 之后是错的**：`confirm` 是一个真实的人当场作出的决定，自动机制不该反过来推翻它；否则人点了「允许」系统仍按拒绝处理，确认框就成了摆设。

**只收紧三类动作**（网络外发 / 读取凭据 / 写入记忆文件），判据是「一旦发生就收不回来」。`write` 一个普通源码文件、`ls`、`git status` 都在外面——它们可撤销、可由人复核。**误报成本是不对称的**：多收紧一类动作，就是多一类「本该能做的事突然做不了」，而 CLI 里没有确认交互可以纠正；漏判只是少一层告警，沙箱/危险命令/第三方授权这些确定性门禁照常生效。所以阈值往「宁可漏判」那边偏。

**怎么把误报率从不可用调到可用**（这段最能体现工程判断）：第一版规则是**关键词命中**——`secret`、`token`、裸提 `CLAUDE.md` 都算。拿自家仓库实测：**45 个文件里 27 个报命中、13 个判 high**。这种扫描器上线就是路障。改法不是调阈值，是换判据：

1. **同现，而不是命中**。`exfiltration` 要求「凭据名词 + 外发动词」在**同一行 80 字符内**同时出现；`memory_poisoning` 要求「记忆文件名 + 写动词」同现。单提一个 `.env` 不算信号——一个把 `.env` 写进文档的项目满地都是 `.env`。
2. **按证据强度分级，而不是数命中条数**。不可见字符 / 伪造的 `<system>` 帧 / 「用户已批准」这类**物证**单独一条就判 high（正常技术文本里不该出现）；单独一句「忽略之前的指令」可能只是文档在举例，要配上第二类信号才升级。
3. **一条规则可以只做告警、不作为升级依据**。`memory_poisoning` 的模式是「写动词 + 记忆文件名」——而这正是**本项目自己文档里反复描述的正常行为**（「约定会被写入 `CLAUDE.md`」）。一条会把「描述自己」判成攻击的规则，不能用来抬阈值。

改完实测：**85 个文件里 9 个报 medium 以上、1 个 high**——那一个是 `security.py` 自己（里面逐字写着这些模式）。这些数字来自 `tests/test_security.py` 里一个**自建回归样例集**（payload 21 条必命中、良性 8 条必不判 high、2 条已知误报钉死），测试直接打印并断言真实计数。**它是自建样例，不是基准，不构成检出率。**

**污染标记有两个刻意的设计**：它是**会话级、粗粒度**的（整个会话一个级别），不是逐值数据流追踪——做不到「这个字符串来自不可信来源、那个没有」；而且 `AgentState` 上**没有 `set_taint`**。不存在的 API 无法被某条代码路径误用去擦掉标记，唯一复位者是人的动作（CLI `--clear-taint`），复位本身还会往轨迹里写 `taint_cleared`，所以 `--resume` 时从事件重算不会被旧的 `security_finding` 抬回去（重放语义，不是取 max——取 max 会让人类已复位的标记复活）。

**告警层必须 fail-open**。`run_post` 在只读工具的 `ThreadPoolExecutor.map` 里被调用，**没有 try/except**——一个正则异常会顺着 map 冒到 loop 的兜底 `except`，把整轮任务判成 `error`。这是写测试时才发现的真问题（原本的测试期望 fail-open，跑出来却是任务终止 + 轨迹里零事件）。**一个把任务搞挂的安全特性，比它想防的问题更糟**，所以钩子里兜住异常、记 `security_scan_error` 事件、返回一条写明「本步骤没有经过模式检查」的横幅——失败是**可见的**，不是静默的。

**最值得讲的一段：「单测全绿，机制却不工作」**（这是真跑真模型才挖出来的，比任何设计陈述都有说服力）。污染天花板写好后，权限相关的测试全过——因为**我的测试和我自己的判据共享同一个盲区**：测试里读凭据用的是 `cat .env`。真拿 DeepSeek 跑注入场景时，模型读 `.env` 用的是：

```bash
findstr /r /c:"^[A-Za-z_]" .env      # Windows 上 grep 的自然替代
```

而当时的判据要求「读动词 + 凭据路径」同现，动词表是 `cat|type|head|tail|less|more|Get-Content|gc`——**`findstr` 不在表里，天花板完全没生效**：命令正常执行、变量名进了模型上下文，轨迹里连一条 `gate_block` 都没有。修的过程也有反复：第一版去掉动词表、只按锚定的凭据路径判，结果 `copy .env x.txt` 漏了（末尾是 `x.txt`），而「把凭据文件当输入写到别处」正是最典型的带离手段。最终判据收敛成一句话：**high 会话里，提到凭据文件的 bash 命令都要人工确认**（不锚定末尾）。代价是 `grep -rn "\.env" README.md` 这种只是提及的也会被拦——这是**故意的**，因为一句话能讲清的规则比一张要不断补的动词表可靠（枚举读动词是打地鼠：`findstr`/`Select-String`/`grep`/`awk`/`sed`/`od`/`strings`/`python -c`…），而解除只要人一句 `--clear-taint`。

同一轮真跑还挖出第二个同类 bug：拒绝文案指引用户「用 `--clear-taint` 复位标记再重试」，但 `--resume` **静默丢掉**了位置参数（`run_from` 用的是 `state.task`）——复位之后 CLI 没有任何办法把「我已复位，请重试」送进会话。**模型按文案停下等人，人却回不了话**，整条「收紧 → 人解锁 → 重试」的动线断在最后一步。教训是：**一条走不通的解除指引，比没有指引更糟**——它让人以为机制已经放开了，实际只是没人接话。

这两个 bug 的共性值得单独说：它们都不是「逻辑写错」，而是**机制写了、单测过了、真跑才发现没生效**。单测和判据是同一个脑子写的，会共享盲区；只有真跑真模型才会用出你没预料到的写法。这也是我坚持「每条验证都要在报告里如实写明跑过/没跑过」的原因。

**最后一定要主动说局限**（README 有整整一节「已知未修复的绕过路径」，S1–S16 逐条可复现，S6–S10 每条都配了 22 条命令的探针实测结果）。安全机制的可信度不来自「实现了什么」，而来自**它挡不住什么被写清楚了**：文本规则换个说法就绕过、记忆文件仍原样进 system prompt、MCP 工具不受沙箱约束、「子代理」是受限只读工具集而不是沙箱、环境变量清洗是按名黑名单（改个名就漏）。**最该主动交代的一条**：bash 的 `command` 参数**根本不经过路径沙箱**——沙箱是「工具层的路径解析」，bash 把它整个绕过去了。实测工作区里 `type ..\.env` 返回 336 字节、内容含真实 key，而 `read` 工具读同一路径被硬 deny。主动列出来比等人问出来强得多，也是这个项目「不造假数据」这条红线的直接体现。

## 6. 记忆（分层 + 自进化）

**分层**（低 → 高优先级）：`CODEAGENT.md` < `MINI.md` < `CLAUDE.md` < `.codeagent/rules/*.md`（`learned.md` 排最后 = 最高优先级）。逻辑是：**离当前工作区越近的知识越该被信任**。

**@include**：`@相对路径` 递归原位展开。安全边界值得讲：只接受相对路径，**显式拒绝绝对路径、`..` 段（含 `sub/../x` 这种伪装）、沙箱逃逸**；循环 include 用 seen 集合检测；文件缺失给占位注释而不是报错——**记忆文件坏了不该让整个任务崩掉**。

**去重 + 预算**：内容 sha256 去重（重复时保留靠后=高优先级那份）；单文件 8K、总计 20K 预算，超了截断并**明确提示**。

**自进化（这条最有意思）**：任务结束后从轨迹里提炼约定（`extract_conventions`）→ `consolidate`（归一化 + 子串包含合并 + hash 去重）→ 写回 `learned.md` → **下次 `discover` 自动包含**。所以约定**跨会话生效**。参考实现里 MiniCode 只有「加载记忆」没有「写回记忆」，这是我认为该补上的一环——**记忆不进化就只是配置**。

## 7. research 子代理（上下文经济学 + 多智能体编排）

**理论依据**（飞书那篇 CC 分析里的原话）：一个复杂任务需要输入 X、过程累积 Y、产出结论 Z。跑 N 个，主上下文累积 `(X+Y+Z)×N`；SubAgent 把 `(X+Y)×N` 外包，**主上下文只收 Z**。

**实现要点**：
- **独立上下文**：子代理有自己的 `AgentState`，与主循环的 messages / usage / compact 完全隔离；
- **受限只读**：白名单只给 `glob` / `grep` / `read`；`_restricted_registry` **永不包含任何子代理工具** → 从结构上禁止无限递归（比运行时判断"深度<3"更可靠）。**用白名单不用黑名单**，因为黑名单在"以后加了新工具"时会静默失效；
- **复用循环**：内部直接跑同一个 `QueryEngine`，不复制代码；
- **失败如实**：超步或异常返回 `ToolResult.fail`，**不假装成功**，主模型据此决定自己上手。

**追问：子代理会不会失控？** 三道闸：只读工具白名单、`max_steps=10`、无 subagent 工具（禁递归）。子代理**不能改任何文件**——所有修改必须由主循环完成，这也是 Claude Code coordinator 模式的原则（worker 只读，root 负责写）。

### 7.1 句柄式并发（M9-7）—— 这一节要能讲"为什么"而不只是"有什么"

M4 只有一个**阻塞**的 `subagent` 工具，跑完才返回。M9-7 把它扩成**句柄式**的五个工具：
`spawn_agent` 立刻返回 `sa-1`、`wait_agent` 收结论、`close_agent` 叫停、`list_agents` 看花名册，
外加保留 `subagent` 作为兼容入口。五个**共用唯一构造点** `build_subagent_tools`
（受限 registry 的构建、步数上限、系统提示词、abort 接线、落盘 store 只写一份）。

**最该讲的三条设计决定**：

1. **`wait` 和 `close` 是两件事。** `wait_agent(timeout_ms=...)` 超时**只回报当下状态、不关闭** worker，
   可以再等一次。把"等够了"和"叫停"混在一起，等于用一个不耐烦的超时去赌它的死活。
   而 `close_agent` 是 abort + **等它真的停下来**才返回（不是"叫过它了"）。
2. **`wait_agent()` 不带 ids 时收的是「还没交回」而不是「还在跑」。** 判据是"交付过没有"
   （`reported`）而不是状态：一次 `[spawn×3, wait]` 里，**第一个 worker 完全可能在 `wait_agent`
   真正跑起来之前就自己跑完了** —— 只看 running 会让它被跳过、**结论静默丢失**。
   已交付过的不再返回（同一条信息出现第二次，白占 token 还破坏前缀缓存）。
   > 这条是**写测试时被逼出来的真 bug**，不是我一开始想对的。值得主动讲。
3. **回合边界结算 = 一个 `finally`。** `AgentWorkers` 每回合新建，`settle()` 写在 `finally` 里，
   **一个地方覆盖 6 个返回点 + `KeyboardInterrupt`**（`except Exception` 抓不到
   `KeyboardInterrupt`，而 Ctrl+C 恰恰是最需要结算的那一刻）。不做的话 worker 会**活过它的回合、
   结论无处可去** —— 那正是这个项目一路在防的头号缺陷类。

**这一项的"牙齿检查"（变异测试，29/29）挖出来的不是产品 bug，是我自己两条测试缺陷 —— 更值得讲**：

- **一条变异体 MISS，而我的第一次修法也是错的。** 「`wait` 超时顺手把 worker 关掉」这条变异最初
  没被抓住。第一层原因好懂：那个用例的假 runner 自己写着"交结论时**不看 token**"（模拟卡在网络调用里），
  所以把 token 置位对它是个 no-op —— **这条契约被断言在了一个结构上根本观察不到它的场景里**。
  但**改完仍然 MISS**，第二层原因才是关键：那条变异锚在 `remaining <= 0` 分支上，而它在
  **逐个 handle 的循环里** —— **只有一个 handle 时循环只走一圈，超时全被 `finished.wait(remaining)`
  吃掉，那条分支根本到不了**。修法是改成**三个** token-aware worker（让前面那个慢的耗光预算）。
  **结论不是"断言太松"，是"场景压根没覆盖到"** —— 这两者要分开诊断，修法完全不同。
- **另一条变异体是 SKIP（锚点没找到），而它差一点就被当成"覆盖了"。** 锚点写成了 16 空格缩进，
  真代码在 `with self._lock:` 体内是 12 空格 —— **它从来没有真正跑过**。教训：
  **SKIP 和 MISS 一样要当失败看**，否则一个坏锚点会伪装成覆盖率。
- **还有一条是"靠竞态抓住的"，我把它改成了确定性。** 用例原先先开闸门再调 `wait()`，worker 有起跑优势，
  重跑可能翻盘；改成由 `threading.Timer(0.2)` 稍后开闸 —— 若 `wait()` 不等就返回，拿到的必然是
  `running`，裕度远大于抖动。**"能抓住但偶尔抓不住"和"能抓住"在交付物上不是一回事。**

**追问：为什么不干脆让它跨回合活着？** 因为"父一定还在"的时刻只有回合边界。跨回合的话，
下一回合的 `messages` 里没有任何东西能接住一个突然冒出来的结论（模型已经给过终局答复了），
而"自动把结论塞回 messages"等于替模型决定它该看什么。所以选择是：**结算它，并把"结论被丢了"
这件事以 `subagent_settled` 事件推到人眼前** —— 有损，但不静默。

**追问：并发真能加速吗？** 实测过一个前置探针（4 条并发 `chat()`，共用同一个客户端）：
**无串台、usage 各自可信**。但要注意两个坑：① 第一次跑出来"并发比串行慢 3.6 倍"，查下来是
**冷启动**（第一条真请求付了 39.92s 的 DNS+TLS+连接池成本，全落在先跑的那一批头上）——
预热之后是 **1.88x**；② 这是**短请求**的观测值，服务端排队与网络抖动都会影响它，
**不要当成常数引用**。这条讲的其实是方法论：
**先把测量方法里的混淆项排掉，再下结论。**

**多步子代理动线的对照**（同样是 DeepSeek 官方通路，同一台机、两条动线背靠背跑）：
同一个"分别调查三个文件"的任务，**并发（`spawn_agent`×3 + 一次 `wait_agent`）17.4s / 3 步**，
**串行（`subagent`×3）29.2s / 4 步**，**加速比 1.68x**。比这个数字更值得讲的是**为什么快**：
`spawn_agent` 四次实测耗时是 **0 / 5 / 0 / 0 毫秒**，而串行 `subagent` 是
**5540 / 7686 / 7426 毫秒** —— 差的不是模型快慢，是**句柄这条契约本身**：spawn 只登记并起线程就返回，
墙钟由"最慢的那个 worker"决定，而不是三者之和。**同时也如实说清它的边界**：这三个子任务都是
"读几个文件、写一份结论"的短活，**1.68x 不是常数**；子任务越不均匀，并发收益越小（最慢的那个决定墙钟），
而且并发与串行是**两条不同的会话**，缓存命中率（44% vs 64%）只能当同向现象读、不是受控对照。

**追问：子代理的 token 算谁的？** 计入**父会话**（`state.usage`），且**只在父线程合并** ——
`Usage.__iadd__` 是四个字段各一次 read-modify-write、**不是原子的**，在 worker 线程里合并会丢更新，
也会与主循环的 `state.usage += result.usage` 赛跑。代价如实说：worker 的 prompt 大多缓存未命中，
会把父会话的**缓存命中率稀释**（README S26）。

## 8. 评估（最容易被追问的一节）

**为什么评估重要**：agent 项目最容易自嗨——demo 跑通一个例子就说"能用"。但**改得对不对必须有客观判定**。

**我的评估集怎么来的**（这条一定要讲清楚，是加分项）：读 tinydb 的真实 git history，筛出「subject 含 fix 关键字 **且**同时改了源码和 tests」的提交，然后：

| 要素 | 取值 | 为什么 |
|---|---|---|
| 任务描述 | 该提交的 subject + body | **真实的 bug 报告**（当时开发者自己写的），不重写成谜语 |
| 起始状态 | 该提交的**父提交** | bug 确实存在的状态 |
| 判分依据 | 该提交里 `tests/` 的内容 | **隐藏测试**，agent 全程看不到 |

**这绕开了 SWE-bench 类任务的两个经典陷阱**：
1. **测试泄漏**——判定用的测试如果 agent 能读到，就是开卷考试。这里隐藏测试只在 judge 阶段写回。
2. **任务描述失真**——把真实 bug 改写成谜语，会让任务变得不可解（连人都不确定要什么）。

**工程细节**：`git worktree add --detach` 给每个任务独立工作区（不污染主仓库），跑完 `remove_worktree` 清理；成本按 DeepSeek 公开定价 + **实测 usage** 估算；**agent 异常或 judge 异常如实写进报告的 `error` 字段**。

**被追问「完成率多少」时怎么答**（诚实很重要）：
> 真实跑分需要 API key，我不想编一个数字给你。**mock 冒烟下完成率是 0%——这是正确的判定结果**，因为 mock 模型根本不修 bug，它验证的是管线连通性。报告里的数字要么是实测的，要么标注为待跑。

## 9. 工具系统

**协议**：`name` / `description` / `Input`（pydantic v2 model，自动生成 JSON Schema）/ `execute` / `is_read_only()`。用 pydantic 对齐 Claude Code 的 zod `inputSchema`。

**两个设计细节**：

1. **参数扁平化**：工具参数不用嵌套结构，避免生成的 schema 出现 `$defs` 引用。**有些模型的 function calling 对 `$ref` 支持不好**，扁平化是最省事的兼容手段。
2. **edit 的唯一匹配语义**：匹配到 0 处或 >1 处都判定失败，并把原因（以及 diff 上下文）回喂给模型。这样模型能自己修正——比「模糊替换」安全得多（模糊替换会改错地方，而且**静默**）。

**截断必须可感知**：`glob`/`grep` 结果截断时，返回里明确告诉模型「还有更多，用更精确的模式」。**静默截断是最危险的**——模型会以为它看到了全部，然后基于不完整信息做决策。

**联网工具（M9-2）**：`web_fetch` / `web_search` 两个工具，重点不在"能联网"，而在**模型给出 URL 意味着这是一个不可信输入**：

1. **SSRF 判据在工具内部、且在发请求之前**——判「这个地址能不能碰」是确定性的，与权限判定无关（详细应答见第 10 节的联网问题）。
2. **它让一条已有机制第一次有了真实对象**：污染天花板收紧的三类不可逆动作里，「网络外发」这一类在此之前只能靠 bash 命令行里的 `curl|wget` 命中，而默认工具集里一个联网工具都没有——**一个挂着却打不到动作的天花板**。接线时有个位置陷阱：判据函数只取 `command`/`path`/`pattern` 三个键，web 工具的参数是 `url`/`query`，所以分支必须写在取这些键**之前**，写在后面等于永远返回 None，**而且单测不会变红**。
3. **内容编码是一个真跑挖出来的 bug，值得单讲**：抓 `python.org` 回来一片乱码。查下来是服务端在**我们没请求压缩**的情况下回了 `Content-Encoding: gzip`，而 `Content-Type` 是 `text/html` —— 于是 2MB 压缩字节通过了文本检查、被当正文解码后喂给模型。**坏数据静默到达消费者**，是我这个项目最警惕的失效形态。修法是三件：请求头声明不要压缩（减少该情况，但服务端可以不听）、真解压且**解压后也要封顶**（原上限只管读进来的字节，压缩炸弹能解出几 GB）、**认不出的编码如实报错而不是退回原文**。

## 10. 可能的压力问题与回答

**Q：你这不就是把 Claude Code 抄了一遍吗？**
> 架构是参考，实现和取舍是我自己的。而且有几个地方我是**明确做了不同选择**的：cache-aware 布局 + 缓存省钱指标（Claude Code 没有面向 DeepSeek 缓存做布局优化）、step 级检查点（它是会话级 resume）、轨迹驱动评估（它没有内置评估）、记忆自进化写回。这些都在 architecture.md 的映射表里逐条标了差异。

**Q：为什么不用向量 RAG 做代码检索？**
> 因为**代码检索用精确匹配比向量更准**——Claude Code 自己就是 grep/glob/read。函数名、变量名是精确符号，不是语义相近的自然语言。加一层向量库会引入 embedding 成本、索引维护、召回不准三个问题，收益却不如一个写好的 grep。

**Q：如果上下文还是爆了怎么办？**
> 四层：0.70 **分级截断**（先缩内容，不删消息）→ 仍超则确定性 snip → 0.85 LLM 摘要 → 超大工具结果**落盘**只留预览+路径（不丢信息）。加上 `max_steps` 硬上限，最坏情况是任务中止并如实报告，**不会无限烧 token**。

**Q：怎么保证 agent 不假装完成？**
> system prompt 里明确要求「不要假装完成，必须实际验证，验证失败要报告」；更硬的保障是结构性的——评估时用**隐藏测试**判分，它说完成了但测试没过，就是 0 分。**判断权不在模型手里**。

**Q：你怎么知道你的某个改动真的有效？有没有过"改了但没效果"的情况？**
> 有过，而且我把它记在 TASKS.md 里了。真实模型验证时我遇到 agent 猜 `/workspace`、遍历磁盘找路径的情况，就往 system prompt 里注入了工作目录，commit message 写的是「修 `--resume` 迷路的真根因」。
> 后来我用**同一任务、同一仓库、只换 system prompt** 做了 A/B（新旧 prompt 各跑一遍，扫描轨迹里的「瞎猜路径」模式），结果是：**步数没有差别**（6 步 vs 6 步，两边都修好、两边都没瞎猜），`--resume` 续跑场景也**没有差别**（都续跑 3 步）。
> 我没改历史，而是追加了一条更正：这次改动如实定性为**防御性健壮性改进**，而不是"修掉了一个 bug、步数下降"。
> 但实验也捞到了一个**真的差异**：我加了一个机制探针（任务是"把工作目录的绝对路径写进文件"），新 prompt 写**对**，旧 prompt 写**错**。顺着这个差异查下去，发现根因是 Windows 上 `pwd` 被 Git for Windows 的 `pwd.exe` 抢占，返回 `/d/RAG项目/...` 这种 **POSIX 路径**——在这台机器上根本不是合法路径，而 `cd`（不带参数）返回的才是 `D:\RAG项目\...`。于是把「确认当前目录用 `cd`，不要用 `pwd`」补进平台提示。
> 我的体会是：**"改动有道理"和"改动有收益"是两件事**，只有 A/B 能把它们分开；而 A/B 跑出来没差别时，正确的做法是更正口径，不是换个指标继续声称。

**Q：你是怎么防止 prompt 注入的？**
> **我没有防止 prompt 注入，我认为在这个架构里防不住**——注入的载体是不可信文本，而文本分类改一个词就能绕过，规则不可能穷举。所以我把问题拆成了两半：**能不能骗过模型，不由我的代码决定；被骗之后还能不能读走 key、发出去、写进记忆，由门禁决定。**
> 具体是三件事：
> ① **结构性加固**（确定性，零误报风险）。最有代表性的一条：`load_dotenv()` 把 API key 灌进 `os.environ`，而 `subprocess.run` 默认继承父进程环境——`echo %DEEPSEEK_API_KEY%` 一条命令就能把 key 打出来，**完全不需要读任何文件**。这是最短的外泄路径。修法是子进程环境按名清洗。另外第三方 MCP 工具改成必须显式 `allow` 才免确认（之前是零策略放行）。
> ② **检测器**（概率性，只出告警）。7 类文本模式，但判据是**同现**而不是关键词命中——「凭据名词 + 外发动词」在同行 80 字符内同时出现才算，单提一个 `.env` 不算信号。第一版是关键词命中，拿自家仓库实测 45 个文件里 27 个报命中、13 个判 high，**这种扫描器上线就是路障**；换判据之后降到 85 个文件里 9 个报、1 个 high（那一个是它自己的源码，因为里面逐字写着这些模式）。
> ③ **后置天花板**（确定性，真正的执行点）。标记为 `high` 的会话里，**网络外发 / 读取凭据 / 写入记忆文件**三类不可逆动作从 `ALLOW` 降为 `ASK`，位置在决策链的**记忆之后、人工确认之前**。
>
> 最容易被追问的是第 ③ 条的位置，也是我踩过的坑：**不能写成规则链里的一条**，因为 `allow_always` 会在它之前短路——用户只要开过一次「总是允许」，任何基于规则的收紧就永久失效，而「记得越久越省事」正是用户去开它的原因。反过来也不能放在人工确认之后，那会让人点了「允许」系统仍按拒绝处理，确认框变成摆设。
>
> 还有一条我认为最重要的：**README 里有一节「已知未修复的绕过路径」，16 条逐条可复现**——文本规则换个说法就绕过、记忆文件仍原样进 system prompt、MCP 工具不受沙箱约束、环境变量清洗是按名黑名单改个名就漏。安全机制的可信度不来自「实现了什么」，而来自**它挡不住什么被写清楚了**。我宁可拿着一张诚实的边界表去讲，也不想声称一个我做不到的能力。

**Q：你给 agent 加了联网工具，那它被诱导去访问内网怎么办？**
> 这是**两条互不替代的线**，我一开始就把它分开了：
> ① **工具内部判「这个地址能不能碰」**（`web.py` 的 `_blocked_reason`，确定性，恒定生效）。判据的支点是「**先解析域名、再判结果 IP**」，不是判 hostname 字面量——后者是漏的，而且是**安静地漏**：我实测过一个域名字面量里毫无内网字样、却解析到 `127.0.0.1` 的。解析失败一律拒绝（fail-closed），因为「无从判断」时放行等于没有判据。
> ② **权限层判「这次外发要不要人点头」**（`high` 污染时收紧），这跟上面那条是两件事：前者管"打内网"，后者管"数据出去"。
>
> 几个我实测过、不查文档就写不对的点：`::ffff:100.64.0.1` 只有把 `ipv4_mapped` 拆开递归判才拦得住（它自己 `is_private` 是 False），但 `::ffff:8.8.8.8` 必须放行，所以不能把整段 `::ffff:` 拉黑；NAT64 和 6to4 前缀**整段**被标成 reserved/private，直接判会把合法映射一起拦掉——那意味着纯 IPv6 + DNS64 的网络（手机网络常见）上工具完全不可用，而且报的是「目标是内网地址」这条**错误的**诊断，所以要把内嵌的 IPv4 拆出来判，位偏移按 RFC 取（取错就等于开一个洞）。
>
> 最容易被忽略的是**位置**：判据必须在发请求**之前**，而且**每一跳重定向都要重查**。只数跳数不校验目标是完全不设防的——**一次跳转就够**：首跳是个货真价实的公网地址，`https://某站/redirect?to=http://169.254.169.254/` 会被自动跟随，云元数据端点就在后面。我拿真实的 `httpbin.org/redirect-to` 打过这个形态，在跳转处被拦。顺带说一句，我读过的一个 Python 移植版把「限制重定向次数」注释成"防止 SSRF"——**那个上限对 SSRF 一点用都没有**。

**Q：这个项目最大的技术难点是什么？**
> 上下文治理里的**记账准确性**。一开始我按消息全量估算 token，但估算偏差会累积，导致 compact 触发时机完全不对——要么该压不压（爆上下文），要么过早压（白丢信息）。改成 provider 实测值做锚点、只估尾部之后，触发时机才稳定。另一个坑是 compact 后忘了把旧 usage 标 stale，结果用压缩前的 usage 度量压缩后的上下文，utilization 直接算错。

**Q：下一步会做什么？**
> 先给准确的状态：**`TASKS.md` 的里程碑清单现在是空的，没有未开工项** —— 这不是"没得做"，是所有评估过的项要么做完、要么**明确不做并留了理由**。所以更诚实的答法是「如果还要做，候选是什么、为什么我现在不做」，而不是硬凑两个方向出来：
> ① **⑤ Loop**（「每 N 分钟重复一次提示词」这类定时驱动）—— 它与 Goal **抢同一个回合执行器**：TS 原版为此写了三处互斥守卫（`session-runtime.ts:84`「Pause or clear the Goal before starting a Loop…」、`:132` 的 `assertIdle()`、以及 Loop 自己的 `busy` 谓词里含 `goal.enabled`）。实现它要多维护三条互斥不变式，还会把 M9-6 那条「一拍 = 一次授权」变复杂。**定时器人人都写得出来，贵的是那三条不变式**，所以排到最后；
> ② **⑥ 全屏 TUI**——真成本不是"终端渲染的体力活"，而是**第二个前端自带一整套状态机**（参照的 Python 移植版 `minicode/tui/` 有 19 个模块，Windows 上还要 `ctypes` 开 VT、用 console API 逐键读）。它还自带一条 `event → session JSONL → 重放` 的第二条渲染通路，与 REPL 的渲染会漂移。**唯一从它里面单独放行的一小块（行式 REPL 的 `readline` 输入历史）已经随 M9-5 做掉了** —— 几十行，吃掉观感差距的大半。
>
> （M8 之前列在这里的「计划持久化 / 提问暂停 / skills / 分级截断」四项已完成；M9 的「改动前 diff 复核」「联网工具 + SSRF 拦截」「step 级分叉 + 会话命名」「MCP 远程 HTTP 传输 + resources/prompts」「常驻交互模式 REPL」「④ 进程内 Goal」「② 并发子代理」**和「工作区回滚快照（M9-8，12 项清单之外新立的）」**也已完成，见第 9 节、第 11 节和第 12 节演示动线。）
>
> ⚠️ **这里我更正过自己一句话。** 之前这一条我写的是「④ Goal（**目标任务树**）——把小任务规划从平铺清单升级成树，允许中途改结构」，但**那句话没有依据**：TS 原版 ④ 的唯一证据（`docs/reference/minicode-notes.md:141`）写的是「进程内 Goal（跨回合推进 + 暂停/恢复/完成检查）」+ 一套 `/goal` 命令族 + `goal/context.ts`——**是一个带状态机的目标对象，没有任何层级结构**，全仓搜 `isComplete` / 停止条件 / 任务树 / `TodoWrite` 零命中。我是被"目标"这个名字带偏的。所以真做的时候按证据的形状做（单一目标 + 状态机），没有造一棵树；而「允许中途改结构」现有 `update_plan`（每次传完整清单）本来就能做。**这件事我留着讲，因为它比"我做对了"更值得说：一个听起来合理的名词，能让一句没有依据的话在文档里躺很久。**

**Q：多回合（常驻模式）和单发跑两次，有区别吗？**
> 有，而且区别不在功能上 —— **同一个 `AgentState` 连跑两次，会把四处「单发时结构上不可观测」的问题一次性暴露出来**。这几个都是我自己写代码时留下的，全是静默失效：
> ① `terminated_reason` 从不复位（单发时"一个回合"和"一个进程"是同一件事，所以从没有过清空动作），第二回合全程带着上一回合的旧值；
> ② 权限的「本回合」永不过期 —— `PermissionsEngine._turn` 全仓零 clear，而单发路径上它随进程一起消失，所以测试里把"回合结束"定义成**新建实例**。常驻进程里 `allow_turn` 就变成了**永久放行**，跟确认框上写的「2) 本回合允许」直接矛盾；
> ③ skill 发现的去重守卫认的是"block 在不在 prompt 里"，而第二回合 block 还在 → 每回合往轨迹里再写一份；
> ④ 回合中途 Ctrl+C 会让 `messages` 停在 `assistant(tool_calls=[3 个])` + 1 条 tool 结果，下一轮请求直接 400 —— 而**报错发生在下一回合**，跟那次 Ctrl+C 看起来毫无关系。
>
> 所以 REPL 那一项真正的产出不是"多了个交互界面"，是**这四条契约**。每一步都有测试钉着，也逐条做了变异（打断机制确认对应测试真的变红）。

**Q：你的目标功能，怎么保证模型不是自己说一句"我做完了"就算完？**
> 靠**把判分权拿走**，而不是靠提示词劝它诚实。具体三层：
> ① **目标只能由人创建**，判据（`--check` 后面那条命令）也是人给的，模型改不了。它只有一个工具 `declare_goal_done`——名字刻意不叫 `complete_goal`，因为工具 description 是这条能力在**唯一常驻请求**里的全部说明，而 `complete_goal` 读起来像"调用它 = 完成"；
> ② **声明只触发一次真实执行**：运行时随即把那条命令跑一遍（走**同一条门禁链**，hooks / 权限 / 污染天花板一并生效），**退出码 0 才算完成**；
> ③ **判定是三态**：通过 / 未通过 / **判定无效**（命令压根没跑成）。未通过**不是终止**——输出尾部 40 行以 `user` 消息回喂，它在同一回合里接着修。
>
> 顺带一个真跑记录：我给了一条**数学上不可能成立**的测试断言，模型算对了 2.0 却看不懂那条断言，于是反复探测烧掉 15 万 token 撞上 `max_steps`——**它始终没有谎报完成**，一直说"测试失败、我还没修好"。这说明「谎报会被当场拆穿」这条设计是有效的。同时也说明另一件事：**agent 卡住时，先怀疑任务和判据，再怀疑 agent。**

**Q：Goal 这块你读过原版实现吗？和原版有什么不同？**
> 读过（`F:\MiniCode-main\src\goal\manager.ts` + `controller.ts` + `tools/goal.ts`）。**原版和我的判分权是反的**，这是这一项我最想讲的一处取舍。
>
> 原版的注释写得很清楚：`/** The user owns the objective; the model can only plan and report its outcome. */` —— 但真读代码，**判分权其实在模型手里**：它给模型两个工具，`get_goal`（读目标和 Plan 快照）和 `update_goal`，后者三个 action —— `set_criteria`（**判据是模型自己设的**）、`blocked`、`completed`（**完成也是模型自己报的**，要带 `summary` 和 `checks`，而且要求**每条判据配一条 check 说明、数量一一对应**）。唯一的"门"是**结构性的**：所有 Todo 必须都 `completed`，否则抛 `Complete planning and every Todo before completing the Goal.`
>
> 我的做法是**把判据也拿走**：人给一条**可执行命令**，退出码说了算，模型只有一个 `declare_goal_done`。两种都成立，取舍不同 —— 原版更灵活（判据可以是"这个设计合理吗"这种**不可执行**的东西），代价是**模型既当运动员又当裁判**；我这条不可执行的判据用不了，换来的是判分权真的不在被考核者手里。
>
> **有一处我们想到一起去了**，值得单独讲：原版 `controller.ts` 第一行注释是 `/** A final is a turn boundary. Only explicit state changes finish a Goal. */` —— 意思是"模型说 final 不算完成，只有显式状态变更才算"。**这和我把"完成"从模型的陈述里拿出来是同一个洞察**，只是它只走到"必须调一个专门的工具 + 走完所有 Todo"，我走到了"退出码说了算"。
>
> 原版有两处比我细，我如实认：① 它有**第四态 `blocked`** —— 模型可以显式报"我卡住了"并**停下来等人**，而我的声明工具只有"完成"一个出口，卡住只能靠 `ask_user` 或撞上限；② 它给模型 `get_goal` 让模型能读回目标和 Plan，我**刻意不给** —— 因为它的判据是模型自己设的、需要读回来，我的判据是人给的、不变，所以不需要。**这个差异正是判分权的直接推论**，可以顺着讲。
>
> 还有一条比"任务树"更值得说的：原版 Goal **绑死 Plan**（`GoalDocument.planId`），Plan 一变 Goal 直接 `clear()`。所以它连"目标 + 平铺清单"都是耦合的 —— **这比我上面更正掉的那个"目标任务树"离真相更远**。

## 11. MCP 客户端（工具生态）

**做了什么**：手写了一个最小 MCP 客户端，能把标准 MCP server 的工具接进来当普通工具用。支持 **stdio 与 Streamable HTTP 两种传输**，覆盖 **tools / resources / prompts 三个能力面**。

**为什么手写而不用官方 `mcp` SDK**（这题一定会被问）：
> ① 官方 SDK 是 **async**（anyio）的，而我的 QueryEngine 是**同步**循环——为了一个工具把整条循环改成 async 不划算，同步版本阻抗最小；
> ② MCP 的协议面很窄（JSON-RPC 2.0 + 十来个方法），手写一遍比封一层 SDK 更透明；HTTP 传输用标准库 `urllib`，与 `tools/web.py` 同一手法；
> ③ 不引入新依赖。

**分层：`Transport`（怎么把消息送出去、拿回来）与 `MCPClient`（说什么）分开。** 这是我加 HTTP 传输时的做法，也是我认为这一项最值得讲的设计判断：协议层（`_request` / `list_tools` / `call_tool` / 会话自愈）**一行没改**。不是洁癖，是**同一个错误不想修两遍**——超时整形、id 关联、错误包装、会话重建这四件事在两种传输上必须完全一致，写两遍必然漂移，而**只测单一传输的套件看不见分歧**。所以有一条测试专门跑同一条操作序列走两种传输，逐项比对结果**和报错文案**。

**一个真实的工程坑**：stdio 读管道**没法设超时**（Windows 上 `select` 也不支持 pipe）。我的解法是给 stdout/stderr 各起一个后台线程持续抽干：stdout 抽到队列里，请求按 `id` 去队列里取（`queue.get(timeout=...)` 天然支持超时）；stderr 抽到环形缓冲——这样出错时能把 **server 自己的报错**带进异常信息，而不是干巴巴一句"超时"。有意思的是 HTTP 侧**不需要**这套：POST 本身同时承担收发，一个请求线程模型就够了。同一个"读超时"问题，两种传输的解法完全不同——这正是把传输抽出来的理由。

**HTTP 侧的三个坑**：
> ① **响应有两种形态**：`application/json`（一条消息）或 `text/event-stream`（若干条，最后一条通常是本次响应）。spec 允许两种，客户端必须都认——只认 JSON 的客户端碰到 SSE 就整个握手失败。
> ② **会话自愈的判断顺序有讲究**：带 `Mcp-Session-Id` 的请求收到 404 时，server 的正文里**常常也放了一条 JSON-RPC error**。如果先判"正文里有 error"，"会话过期"就会被报成一次普通调用失败——文案看着完全合理，但重新 initialize 那条路**永远走不到**，一次 server 重启就废掉整个任务。假 server 特意用这种正文钉住顺序。
> ③ **重定向不能跟随**：`urllib` 默认把 302 上的 POST **改写成 GET**，一次 `tools/call` 会变成一次静默的读请求。宁可报一句能照着改的配置错误。

**如实标注未做的部分**：独立 GET SSE 流（server 主动发起请求那条长连接）与 `Last-Event-ID` 断点续传我**没做**。三个能力面都走 POST 请求-响应，用不到它们；假 server 的 GET 一律回 405，钉住客户端不会偷偷去开。我不想让"HTTP 传输做完了"听起来像"整份 spec 都实现了"。

**安全边界（这是我认为最该讲的一点）**：MCP 工具来自第三方 server，**不受我的 workspace 沙箱约束**。所以：
1. **必须显式配置才注册**（`--mcp`），不进默认工具集；
2. 只读性**只信 server 声明的 `annotations.readOnlyHint`**，没声明就当可写 → 串行执行，绝不并发跑未知副作用；
3. **它们照样走 `_gate_and_run` 门禁链**——权限引擎和 hooks 对 MCP 工具同样生效；
4. **权限默认不放行**：`allow` 里列出来的工具才免确认，其余判定 `ask`（CLI 无交互确认 → 拒绝）。

第 3 点是**分层设计的回报**：接入一个全新的工具来源，循环一行都不用改。如果权限和 hooks 是写死在循环里的，这里就得动核心代码。

**但第 3 点同时是我踩过的坑，也是我更愿意讲的一段**：能走门禁**不等于**门禁有正确的策略。MCP 工具名落到权限引擎里走的是通用 `tool` 分类，而那条路的兜底是 `return ALLOW` —— 于是「接上第三方 server 就默认信任」，第 3 点的分层回报在这里变成了分层的盲区。修法是给 `Tool` 加 `is_external()`，`_classify` 把外部工具单独归一类，`_rule_check` 里 `external` 分支命中白名单才 `ALLOW`、否则 `ASK`。**这一条我是在做注入防御时回头审自己的代码才发现的**：加一个安全特性的时候，顺手审出了三个别的洞（还包括子进程继承 `DEEPSEEK_API_KEY` 环境变量、`run_post` 的返回值被丢弃导致 PostToolUse 那层治理从未到达模型）。我把它们和误报修复一起单独成 commit，没有混进新特性里。
（`url` 我**不做 SSRF 校验**，与 `web_fetch` 刻意不同：那个 URL 是**模型**给的，这个是人写在 `mcp.json` 里的显式 opt-in——校验一个用户自己填的地址没有意义。）

顺带一个设计细节：`allow` 的匹配放在 `load_mcp_servers` 里做，而不是权限引擎里 —— 因为只有那一处同时知道「远端工具名」和「注册名」（与内置工具重名时会加 `<别名>__` 前缀）。否则用户得去猜前缀，配置就成了实现细节的泄漏。

**resources / prompts 两个能力面**（M9-4 补的）：注册条件是**两条都满足**——server 在 `initialize` 里声明了该能力**且列表非空**。只判能力的话，一个声明了 `resources` 却一处资源都没有的 server 会拿到一个**永远调不通**的工具，白占 schema token、模型每次调用都失败一次。这一点**真跑对上了**：DeepWiki 声明了两种能力，两个列表都是空的，于是正确地没注册。另外工具描述里**必须列出可用的 uri / 提示词名与参数名（含必填性）**——不列的话模型不知道有什么可读，只能瞎猜一个试试，而那正是 `update_plan` 上栽过的 elicitation gap 的形状。描述恒在上下文里，列出来是零额外往返；封顶 20 条并如实说"另有 N 处未列出"。

**测试怎么做**：写了一个**真实的假 MCP server**（`tests/fake_mcp_server.py` + `tests/fake_mcp_http_server.py`，共用 `fake_mcp_core.py`）——真子进程、真管道、**真 socket**、真 JSON-RPC 往返。所以测试能覆盖握手、跨进程读超时、server 中途崩溃、SSE 响应、会话过期重握手这些**只有真进程/真连接才会暴露**的问题。还有一个测试让 MCP 工具**经真实 QueryEngine 循环**被调用，验证集成而不只是协议。权限侧另有一组：外部工具默认 `ASK`、授权后 `ALLOW`、拒绝文案里必须含 `mcp.json` 与工具名（拒绝而不说怎么解，只会让 agent 反复重试同一个调用）。

**真跑验证**：stdio 侧接官方 `mcp-server-time` 跑通（并且验证了只改 `allow` 就能让同一任务从"被拒"变成"返回真实时间"）；**HTTP 侧接 DeepWiki 的公开远程端点**（`https://mcp.deepwiki.com/mcp`，走真公网），DeepSeek 实际调用 `read_wiki_structure(repoName=pallets/flask)` 成功，1 步 / 2425ms。这次真跑还挖出一个真 bug：`--mcp` 的相对路径是按进程 CWD 解析的，而 help 里给的例子正是 `.codeagent/mcp.json`——设了 `WORKSPACE_ROOT` 从别处跑就报"配置不存在"。**一句照着文档抄却走不通的指引**，改成按工作区解析并补了测试与变异体。

## 12. 现场演示动线（**菜单，不是一条 5 分钟的路**）

> **口径更正**：这一节原先的标题写的是「5 分钟」。到 M9-8 为止它有 **8 条主线 + 9 条支线**（4j 是 M9-8 新加的），
> 按各自标注的时长加起来是 **22 分钟以上** —— **标题与内容不符本身就是一种漂移**，所以改成菜单。
> **如果只有 10 分钟**（下面这 6 条按各自标注的时长加起来是 **9.5 分钟** —— 这句话原先写的是「5 分钟」，而它列的条目从来就不止 5 分钟），走这条核心：**3（block-at-submit）→ 4（崩溃恢复 → `--resume`）→
> 4g（REPL 多回合）→ 4h（目标 + 显式完成检查）→ 4i（并发子代理）→ 4j（倒带重试）**。
> 这条线的共同点是：每一条都能现场看到**一个机制在起作用**，而不只是"跑通了"。
> 其余条目按面试官的兴趣取用；标了「可选」的通常需要额外环境或时间。

1. **无 key 演示**（30 秒）：`python -m app.cli --mock "读 README 并总结项目结构"` — 真实执行 glob，Mock 给结论
2. **危险命令拦截**（30 秒）：让 agent 跑 `rm -rf /`。**说清是哪一层拦的**：不是 bash 工具自己拒绝，而是权限引擎判定 `ask`，CLI 无交互确认 → loop 按安全默认拒绝，理由回喂模型让它改道。bash 工具里的模式匹配只是**没有权限引擎在场时**的兜底（`ctx.permissions is None` 那条分支）——两条路都存在，但默认走的是权限引擎那条。
   > 顺带可以讲 A7 修的那个误报：原来的危险模式里有 `eval\s`，于是 `echo "medieval times"` 也会被判成危险命令。**误报的代价不是「多问一句」而是「这事做不了」**（CLI 没有确认交互），所以模式要收紧成 `(^|[;&|]\s*)eval\s`。
3. **block-at-submit**（1 分钟）：让 agent 提交代码，看 hook 因测试未通过而阻断
4. **崩溃恢复**（1.5 分钟）：跑长任务 → 中途 `Ctrl+C` → `--resume` 接着跑完，展示检查点文件
4b. **提问 → 暂停 → 续答**（1 分钟，M8）：给一个**信息不足**的任务，看 agent 调 `ask_user` 停下、CLI 用独立的「需要你补充信息」样式打出问题（不是「最终结论」）→ `python -m app.cli --resume "你的回答"` 续跑完成。**这段的讲解点在"打断是数据标志而不是阻塞"**：`ToolResult.await_user` 只是个布尔值，turn 语义由 loop 决定 —— 所以 headless 评测只要**不注册**这个工具就完全不受影响，不需要在循环里写任何 `if headless`。
   > 可选加一句：停在提问处的那一轮**不做约定提炼**（半程轨迹，模型当时正在猜），续跑完成后照常提炼。
4d. **改动前复核**（1 分钟，M9-1）：`python -m app.cli "修掉 calc.py 里的减法 bug" --review-edits` → agent 读完文件后**停下**，把 unified diff 打出来等你选（1 允许一次 / 2 本回合允许 / 3 一直允许 / 4-6 拒绝，**直接回车 = 拒绝**）。**这段的讲解点在"人看到 diff 时磁盘上还是旧内容"** —— `preview` 取在 `permissions.check()` 之前，而且 `preview` 与 `execute` 共用同一份匹配语义，所以不会出现「预览说能改、执行说不唯一」。可以顺手演示拒绝那一侧：答 `4`，文件**原封不动**，模型如实回「补丁已备好但被权限拒绝」。
   > 要说清它为什么是开关而不是默认：我们的 CLI 没有确认回调，把 `edit` 改成默认 `ask` 会让每次改动都退化成拒绝、整条 CLI 不可用（把安全机制变成路障）。TS 原版靠 TTY 模式兜住，我们没有。
4c. **计划清单跨回合**（1 分钟，M8）：`python -m app.cli --plan` 直接看最近会话的计划清单（**不需要 API key**）。配合第 4 条演示：长任务中途 kill → `--resume` 时计划被补投一次。要主动说清 **`update_plan` 每步传的是完整清单**（不是增量），以及**刻意不把计划注入每轮消息**——那会破坏前缀缓存，可见性靠工具结果本身就够了。
4e. **联网任务 + SSRF 拦截**（1.5 分钟，M9-2）：
   ```bash
   CODEAGENT_SEARCH_BACKEND=bing python -m app.cli "查一下 Python 3.13 的发布日期并写进 release.md"
   ```
   看 `web_search` → `web_fetch` → `write` → `read` 四步跑完，产物对着来源可核。
   > **先主动交待一句默认后端**：默认是 `ddg`（对齐 TS 参考实现），但它在境内连不通，所以要显式切 `bing`；而且 **DDG 那条解析路径没有对着真实响应校准过**（连不上就没法校准），这个事实写在代码注释和 TASKS.md 里。**主动说出"哪条路没验证过"，比被问出来强得多。**
   > 然后是可以现场演示的拦截：让 agent 去抓 `http://169.254.169.254/latest/meta-data/`（云元数据端点）——直接被拦，报的是「目标是内网/本机地址（… → 169.254.169.254）」。**更好的演示是重定向那条**：首跳是一个**货真价实的公网地址**（`https://httpbin.org/redirect-to?url=http://169.254.169.254/...`），能过首轮判据，在跳转处被拦——这一条才说明"每一跳都重查"，只看首跳的实现在这里会漏。顺带讲那个反例：**只限跳数不校验目标对 SSRF 一点用没有，一次跳转就够**。
   > 这段的收尾是分层：这个拦截判的是「**能不能碰**」（打内网），和权限层判的「**要不要人点头**」（数据出去，`high` 污染时收紧）是两条互不替代的线。可以接着第 8 条演：把污染抬到 `high` 之后，`web_fetch`/`web_search` 同样被收紧。
4f. **分叉 + 会话命名**（1 分钟，M9-3）：`--sessions` 先看一眼清单（**不需要 key**）→ `--rename "基线方案"` 起个名 → 跑一段 → `--fork --step 3` 从第 3 步分叉（**同样不需要 key**，分叉不动模型），再把生成的续跑命令粘出来跑。
   > **这段的讲解点在"检查点粒度决定了能做什么"**：TS 原版的 fork 是会话级的，我们的挂在 step 级检查点上，所以能**回到任意一步** —— 这是既有设计的推论，不是新写的一套机制。
   > **必须主动说边界**：**单独** `--fork --step 3` 是**对话分叉**，工作区文件**不会**回滚到第 3 步，分叉后的 agent 看到的是当前文件。要让文件也回去就加 `--rewind`（第 4j 条演示）—— CLI 会按有没有 `--rewind` 打印**不同的那一句**。**不说这句，对方几乎必然以为文件也回去了。**
   > 还可以讲 `--sessions` 为什么**不是附赠**：没有它，`--rename` 写的名字和 `--fork` 记的血统**没有任何消费者** —— 机制在、测试绿、文档写了，但没有任何东西把人引到它上面。这是我在这个项目里反复抓的一类缺陷，所以加机制时会先问「谁会看见它」。
4g. **常驻交互模式**（1.5 分钟，M9-5）：`python -m app.cli --repl` 进提示符，然后**故意追问一句** —— 第一回合「跑一下测试，把失败的修好」，第二回合「再补一个测试」。第二回合**不重读源码**就能写出正确改动，这是上下文真的接上了。
   > **这段真正的讲解点不是"多了个交互界面"，是"多回合把四处静默失效逼出来了"**：`terminated_reason` 不复位、`allow_turn` 永不过期、skill 发现每回合重放、中断后 tool 结果配对残缺（详见 §10 那条问答）。**这四个在单发进程里结构上不可能观测到** —— 一个进程只有一个回合，"清空动作"和"回合边界"是同一个东西。所以 REPL 这一项的产出是那四条契约，界面只是把它们变成必经之路。
   > 有三条不变量值得单独说：
   > ① **不认识的斜杠命令绝不发给模型** —— 打错一个字母的代价是一次真实的模型调用，而模型的回答看起来还挺像回事，于是这个错误不会被发现。可以现场敲 `/hlep` 演示：只打印提示、不花钱。
   > ② **`allow_turn` 真的只在本回合有效**。现场验：`--review-edits` 下改一个文件、答「2) 本回合允许」→ 下一回合改**同一个文件** → 确认框**重新弹出**。这条在改动前是坏的（`_turn` 从不清空，答一次就永久放行），而它在单发路径上完全无害，所以测试里"回合结束"当时是拿**新建实例**模拟的。
   > ③ **退出时给的那条续跑命令真能跑**。这是被自己打印的文案逼出来的：检查点是按节拍落的、且只在有工具调用的步上 tick，纯聊天或只走两步就退出会一个检查点都不落，而 CLI 刚刚承诺了「继续: … `--resume --session-id <sid>`」。所以退出时强制落一次。**一条走不通的指引比没有指引更糟**（M7 的教训），这次那条指引是我们自己打的。
   > 顺带一提：`await_user` 在 REPL 里**不需要任何特殊代码** —— 模型提问、本轮结束、打印问题、下一行输入就是回答。这正好是第 4b 条那个「打断是数据标志而不是阻塞控制流」的回报，可以串起来讲。
4h. **进程内目标 + 显式完成检查**（2 分钟，M9-6）：`python -m app.cli --repl` 进提示符，然后设一个**判据可执行**的目标：
   ```
   /goal 让 calc.py 的减法是减法 --check python -m pytest tests/test_calc.py -q
   ```
   看它**自动续跑**（一拍最多 3 回合），模型中途调 `declare_goal_done` **声明**完成 → 运行时**真的把那条命令跑了一遍** → 退出码 0 才打出 `goal_completed`、回合结束。产物可核：`data/sessions/{sid}.jsonl` 里有 `goal_created` / `goal_check`（带 `exit_code` 与 `output_tail`）/ `goal_completed`。
   > **这段唯一要讲清的事：判分权不在模型手里。** 模型只有一个工具 `declare_goal_done`——它**声明**"我觉得成了"，运行时随即跑**人预先给定的**那条命令，`exit 0` 才算完成。模型不能创建目标、不能改判据、不能暂停或清空（同 `clear_taint` 的纪律：**标记不由被标记者清除**）。**这是这一项和"让模型自己说完成了"的全部区别** —— 后者不是机制，是一句话。
   > **判定的三态**是第二个值得讲的点：命令**压根没跑成**（被门禁拦下 / 超时 / 工具异常）单独记一档 `判定无效`，既不算完成也不算未通过。这条教训直接来自 eval 的 `JudgeResult.executed`（pytest 退出码 2/3/4/5 认得出"没跑成"），而 **shell 没有这个信号**（S20）。而**未通过根本不是终止** —— 输出尾部 40 行以 `user` 消息回喂，模型在同一回合里接着修。
   > **同步交待三条边界**，别等人问：① 判据是人给的，运行时**只看退出码、不评价它检查了什么**，`--check "true"` 永远通过（S17，唯一缓解是可见性——命令原文永远印在结果旁边）；② 声明**不是闸门**，只是事后核验——模型可以不声明就把活干完，也可以在毫无证据时声明（S18）；③ 检查走同一条门禁链，所以一次成功的 `pytest` 会写 `data/tests_pass.marker`，从而**替 agent 解锁 `git commit`**（S19，轨迹上这与模型自己跑同一条命令不可区分）。
   > **暂停那条语义要按结构讲，不要按现象讲**：`/goal pause` 的真实后果是「REPL 不再自动续跑」（我们的架构里没有定时器，暂停必须停掉一个**真的在跑**的东西）。但**纯 stdin 流程里你敲不到它** —— 一拍结束时一定已经 `_pause_goal(stop)` 了，所以人拿到提示符时目标**不可能还是 `active`**，那个「人工回合顺便暂停一下」的分支**结构上不可达**（要现场验证得用交互终端）。**这不是 bug，是「一拍 = 一次授权」这条不变式的推论** —— 主动说出来，比被追问出来强。
   > 顺带可以讲那个**测试素材错误**：真跑时模型在一个断言 `median_word_length("a ccc") == 1.5` 上卡住（那是我在**验证工作区**里手写的素材，不是仓库的测试套件）—— 词长 `[1,3]` 中位数必然是 2.0，这条断言**数学上不可能成立**，模型反复探测烧掉 15 万 token 撞上 `max_steps`。**模型始终没有谎报完成** —— 它一直说"测试失败、我还没修好"。这正是这条纪律想要的行为，也说明**agent 卡住时先怀疑任务和判据，再怀疑 agent**。
4i. **并发子代理**（1.5 分钟，M9-7）：`python -m app.cli --repl`，然后一句派三件互不相干的调查：
   ```
   同时派三个子代理分别调查 pkg/alpha.py、pkg/beta.py、pkg/gamma.py，再用一次 wait_agent 收齐，综合成一份报告
   ```
   看它一条消息里发三个 `spawn_agent`（各自立刻返回 `sa-1/2/3`）→ 一次 `wait_agent` → 三份结论一起回来。
   > **这段的讲解点按重要性排**：① **`spawn` 立刻返回**，所以三个 worker 真的同时在跑（不是"看起来像并发"）—— **这条有实测数字，直接报**：同一条任务下 `spawn_agent` 四次耗时是 **0/5/0/0 毫秒**，而串行 `subagent` 是 **5540/7686/7426 毫秒**；整套动线**并发 17.4s vs 串行 29.2s（1.68x）**。**顺手说清 1.68x 不是常数**：这三个子任务都是短活，墙钟由"最慢的那个 worker"决定，子任务越不均匀收益越小；并发与串行还是**两条不同会话**，缓存数字（44% vs 64%）只能当同向现象读；② **`wait` 和 `close` 是两件事** —— 可以演示 `wait_agent(timeout_ms=2000)` 超时先拿到"还在跑"、再 wait 一次拿到结论（超时**不会**把它杀掉）；③ **`close_agent` = abort + 等它真停**，不是"叫过它了"（实测 1140ms 返回、状态 `closed`、没有结论）。
   > **然后主动讲回合边界那条**（这是最容易被追问的）：worker **只活一个回合**。派出去不 wait 就直接回答的话，它会被结算掉 —— 可以现场演示：让 agent「派一个子代理然后不要等，直接告诉我你派了什么」，屏幕上会打出 `subagent_settled` 事件，说明**哪几个结论被丢了**。**有损，但不静默** —— 这就是这一项的设计取向。
   > **最后那条自曝其短会加分**：我最初写的工具描述里有「比三次 `subagent` 快得多」这种没量的断言。写真实探针时第一版测出**并发比串行慢 3.6 倍**，查下来是**冷启动**（第一条真请求付了 39.92s 的 DNS+TLS+连接池成本，全落在先跑的那批头上）；预热后是 **1.88x**。我把那句断言改成了不带形容词的表述，并把探针连同这个坑一起留档。**讲这段比讲"并发更快"有价值得多** —— 它说明我知道"数字要先排除混淆项才能引用"。

4j. **倒带重试（fork + rewind）**（2 分钟，M9-8）：跑一段会改文件的会话（比如第 4 条那个"修 `calc.py`"），然后：
   ```bash
   python -m app.cli --snapshots                          # 先看这台机器攒了多少快照（不需要 key）
   python -m app.cli --fork --step 3 --rewind             # 同一个 K：对话回到第 3 步 + 文件也回到第 3 步
   ```
   **默认只打预览不落盘**（git-diff 风格：哪些文件被覆盖、哪些被删除、**哪些不属于管辖范围**），要 `--force` 或按 `y` 才真写。执行后 CLI 会打一句"已回到第 K 步"，并把续跑命令粘出来。
   > **这段的讲解点在三处，按重要性排**：① **`--fork` 与 `--rewind` 共用同一个 K** —— 不是一个"回文件"的独立功能，而是**检查点坐标系上的一次裁剪**，这也是为什么它能和 `--fork` 拼起来：单独 `--fork` 是对话分叉，加上 `--rewind` 才是"倒带重试"。② **回滚是全项目唯一一个不可逆的写操作**（覆盖文件、删文件，`git` 之外没有第二条退路），所以默认必须是预览 + 二次确认（默认答案是 `n`）—— 这条不是保守，是**"唯一的不可逆操作不配拥有默认执行"**。③ **边界要主动说全**：`bash` 的副作用（起过的进程、改过的数据库、发过的 HTTP 请求）**回不来**，这不是"我们的 bug"，是**可回滚性的边界** —— CLI 会把"不在管辖范围内的文件数"和"回滚区间内的 bash 调用数"**分成两个独立维度**报出来，不合并成一个含糊的"已完全回滚"。
   > **可核的产物**：对象库是**全局共享**的（`data/snapshots/objects/{aa}/{sha}.bin`，内容寻址，跨会话去重），清单是**按会话隔离**的（`data/checkpoints/{sid}/ws/step-N.json`）。实测 `--fork` 的**对象增量是 0 个 / 0 字节**，只多了一份 599 字节的清单 —— 这就是"全局共享对象库"这条设计决定的可观测证据。
   > **被问"加锁了吗"就如实答"没加，且是先测了才决定不加的"**：写路径由父线程独占（worker 结构上不可能写文件），所以唯一可能的冲突是**两个进程同时往对象库写**；实测 40 次裸 `os.replace` 并发冲突 24~30 次（Windows `PermissionError(13)`），但**经 `_put_object` 走完整路径的未捕获异常是 0 次**（内容寻址 → 同名同内容 → 谁先谁后都对）。**先测再决定，不凭想象力加锁** —— 这段说出去比"我加了锁"值钱。

5. **控制台**（1.5 分钟）：`streamlit run app/ui_streamlit.py` — 缓存命中率曲线 + 省钱估算 + 检查点回放
6. **评估**（可选）：`python -m eval.runner --limit 2 --mock` — 展示报告的诚实判定（0% = mock 真没修 bug）
7. **MCP 与第三方工具授权**（可选）：`python -m app.cli --mock --mcp .codeagent/mcp.json "任务"` — 看第三方工具被注册进工具集、走同一套门禁，且**没列进 `allow` 的工具被拒绝**（拒绝文案里带出处和解除方式）。这段可以顺带讲「能走门禁 ≠ 门禁有正确策略」，是第 11 节那个坑的现场版。
   > **想接真远程 server** 就在 `mcp.json` 里写 `"url": "https://mcp.deepwiki.com/mcp"`（公开、无需 key），换成真实 LLM 跑——`read_wiki_structure` 会返回真实的仓库文档结构。这条动线的好处是它**没有本地依赖**：不用装 node、不用起子进程，只走一次 HTTP POST，面试机房里也能跑。
8. **注入检测 + 污染天花板**（可选，1 分钟）：往 workspace 放一个含 payload 的文件（用 `tests/test_security.py` 里的 `POISON` 常量），让 agent 去读它 → 看 CLI 打出「安全观察」横幅、轨迹里出现 `security_finding` → 此时会话标记为 `high`，**网络外发 / 读取凭据 / 写入记忆文件三类动作被收紧**，拒绝文案里带出处 → `--clear-taint` 复位后恢复。
   > 这段要**主动说清三件事**，否则会被当成「你做了注入防御」（说了反而扣分）：① 检测是**概率性**的，换个说法就绕过；② 真正收紧能力的不是检测器，是权限引擎的**后置天花板**（确定性）；③ 它**不阻断工具**，也不锁死普通编辑——第 8 条演示的正确观感是「普通干活全程不受影响」，不是「一命中就瘫痪」。

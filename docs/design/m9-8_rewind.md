## 0. 一句话结论与它真正要解决的问题

**M9-8 不是"加一个 undo 按钮"。它要消灭的是本项目已经真跑见过一次的那个错误：模型说出一句它没有做过的事。**

现场在 M9-5 的 B 动线（`TASKS.md` 的 **M9-5 条目「如实说明未做」第 ② 点** 原话）：`--fork --step 2` 分叉到"修 bug 之前"，
但盘上文件**已经是修好的** —— 于是新分支的模型 `read` 到的是"已修好"的文件，
**却又在结论里说了一遍"修好了失败的测试"**。

这条边界已经写进五处文档（`TASKS.md` 的 M9-3 条目、`docs/architecture.md` §3.6「分叉与命名」、
`docs/interview_guide.md` §4 与 §12 的 4f 条、`docs/TECH_SPEC.md` §9.3b、`CLAUDE.md` 的 M9-3 段），
写的都是**「`/fork` 只分叉对话，工作区文件不回滚」**。M9-8 就是把它从"如实标注"
变成"已修"。

**参照对象要说清楚**：`grep -rn rewind --include=*.ts src/` 在 TS 原版
`F:\MiniCode-main` 下**零命中**（2026-09-12 核实）。rewind **不是原版能力**，
是第三方 Python 移植 `F:\MiniCode-Python-main` 自己加的（`minicode/session.py:82`

判据只能是"我们自己需要什么"。

## 1. 作用范围：什么能回滚，什么不能

这一节是本文档最重要的部分。**一个让人以为"回到过去了"、实际只回滚了一半的
rewind，比没有 rewind 更危险** —— 因为人会据此停止检查。

### 1.1 只有一条通路会被登记

**快照管的是「经 `write` / `edit` 工具成功写盘的文件」。** 这是唯一被登记的通路，
理由是结构性的：这两个工具是**经由门禁链**（`loop._gate_and_run`）执行的唯一写路径，
登记点就挂在门禁链的成功返回处（`agent/loop.py:996` 的 `tool.run(...)` 之后）。
写在别处（比如工具自己内部）会漏掉"权限拒绝的那次调用压根没执行"这个区分。

写盘点各只有一处，没有第二条路：
- `agent/tools/files.py:150` — `WriteTool.execute` 的 `resolved.write_text(...)`
- `agent/tools/files.py:262` — `EditTool.execute` 的 `resolved.write_text(...)`

### 1.2 不能回滚的（要如实列出来，不是免责声明）

| 类别 | 具体是什么 | 为什么回不去 |
|---|---|---|
| **`bash` 的一切副作用** | `rm` / `mv` / `mkdir` / 输出重定向 / `git add`·`git commit` / `pip install` / `pytest` 写的 `.pyc`·`.pytest_cache` | 我们只看得到"命令跑了"，看不到它改了什么。**这是不可回滚范围里最大的一块。** |
| **外部工具体（MCP）的写入** | 一个能写文件的 MCP server 的工具 | 同 bash：`Tool.is_external()` 的工具我们不知道它有没有副作用，也不登记它 |
| **只读工具的外发** | `web_fetch` / `web_search` | 请求已经发出去了，不可撤销。这一项**没有文件系统后果**，列在这里是为了把"范围"说完 |
| **文件系统元数据** | 权限位、mtime、符号链接、**空目录** | 快照存的是**文件内容**，不是目录树。被 `bash rm -rf` 删掉的目录不会回来；被 `bash mkdir` 建的目录也不会被删掉 |
| **进程外的一切** | 另一个终端、编辑器、git hook、别的 agent 会话 | 超出本项目视野 |

### 1.3 可能误导人的四处，以及各自的应对

#### M1 ── 「回滚了 = 什么都没发生」

**最危险的一条。** 一个被 `rm` 掉的文件不会回来；一次 `git commit` 不会撤销；
一个 `mv` 不会自己走回去。而"我刚刚回滚了工作区"这句话在心理上等同于"我按了撤销"。

**应对（三条，都要落进命令输出）：**

1. **回滚前必须先预览，且预览里要有一栏专门讲"不回滚什么"**（§5 的命令面）。
2. **报告里带可计算的证据**，不是一句空话：扫描轨迹事件，把回滚区间内
   **`bash` 调用次数**打出来 ——
   `⚠️ 第 5~9 步里有 4 次 bash 调用，它们的副作用不会回滚。`
   这条数据**能从检查点里真的算出来**（`state.events` 全量进检查点，
   `dump_state` 走 `dataclasses.fields()` 不截断；事件形如
   `{"type":"tool_call","name":"bash","step":7,...}`，见 `agent/loop.py:614-624`）。
   **不是免责声明，是这一轮回滚的现场事实。**
3. **明确不碰 git，并且把这句话说出来**。我们有 PostToolUse 在测试通过时写 marker、
   解锁 `git commit` 的机制（`CLAUDE.md` 的 hooks 段）—— 人很容易顺着联想到
   "rewind 是不是也把 commit 撤了"。答案是不撤，而且要说。

#### M2 ── 对话与工作区错位（★ 最阴的一条）

**回滚文件但不动对话**，模型的上下文里还留着它自己 `read` 到的"改好的文件"
和 `edit` 的成功回执。回滚之后：**模型相信文件是 X，盘上是 Y。**
它会基于 X 继续推理，然后在结论里说出它没做过的事 —— 这正是 §0 那个现场。

这不是新问题，是 M9-5 B 动线的**镜像**：

| | 对话 | 工作区 | 后果 |
|---|---|---|---|
| `--fork --step K`（今天） | 回到第 K 步 | **留在现在** | 模型读到"未来的"文件，说出一句它没做过的事 |
| `--rewind --step K`（只回滚文件） | **留在现在** | 回到第 K 步 | 模型记得"过去的"内容，基于一个已经不在盘上的文件继续推理 |

**两个方向都会让模型说谎。** 所以 M9-8 的答案必须同时处理两个方向，
而不是只把文件搬回去。

**应对（这是本项的核心设计决定）：**

**① 回滚是"就地 + 带坐标"的动作，不是一次孤立的文件搬运。**

回滚记录写进**轨迹事件**（`workspace_rewound`，带 `target_step` 与受影响的文件清单）
—— 轨迹是 append-only，任何时候都写得进去，不依赖 state 落盘。

**② `--resume` 时按坐标补投一条说明（复用项目已有的补投机制）。**

项目里已经有 `_reinject_plan`（`app/cli.py:495`）与 `_reinject_goal`（`app/cli.py:514`）
两个先例，形状是：**恢复时补一次，不每轮贴**（每轮贴会破坏 `_PREFIX_LEN` 之后的前缀缓存）。
M9-8 加第三个 `_reinject_rewind`，触发条件是**精确的**：

> 从检查点读出的步号 **>** 最近一次回滚的目标步 → 说明"对话所在的世界"比"盘上的世界"新，
> **补投**；否则**不补**（对话与工作区本来就同坐标，补一条反而制造困惑）。

补投的文案必须**同时说清三件事**：回滚到了哪一步、**你上下文里关于这些文件的记忆已经过时**、
以及动手前先重新 `read`。

**③ 提供"两个坐标一起回去"的入口（推荐用法，见 §4.1）：**

`--fork --step K --rewind` —— 分叉（对话回到第 K 步）+ 回滚（文件回到第 K 步）。
**这时 M2 消失**，因为两边同坐标。这是 M9-8 最有价值的形态，也是面试时该演示的那一条。

#### M3 ── "半回滚"的假象

agent 用 `bash` 生成了一个文件、又用 `edit` 改了另一个文件。回滚只恢复后者，
而**回滚报告如果只说"恢复了 1 个文件"，人会以为工作区干净了**。

**应对**：报告**分栏**——`恢复` / `删除` / `本来就一致（未动）` / **`不在管辖范围（未动）`**，
最后一栏把"我们没碰过的文件"的数量也报出来（`bash` 新建的文件就落在这里）。
让人一眼看出"这次回滚只覆盖了受管集合里的一部分"。

#### M4 ── `--fork --step K` 和 `--rewind --step K` 的组合预期

两条命令都叫"回到第 K 步"，但**做的不是同一件事**，而且**工作区是物理共享的**：
`--rewind` 改的是盘上的真实文件，**它会影响源会话后续的运行**（fork 不复制工作区，
会话隔离靠的是 `data/` 下的检查点目录，不是工作区副本）。

**应对**：`--rewind` 的输出里固定印一句
`工作区是共享的：这次回滚会影响该工作区上所有会话的后续运行。`
并在 `--rewind --help` 里写明它与 `--fork` 的分工。

### 1.4 术语纪律（写进 help 与所有输出）

- **不叫"撤销 / undo / 时光倒流"**，叫 **「回滚我们写过的文件」**。
- 不说"恢复到第 K 步"，说 **「工作区文件回滚到第 K 步的快照（仅限 `write`/`edit` 写过的文件）」**。
- 不出现"什么都没发生"这类**全称判断**。
- 与项目 M7 的措辞纪律同源：**不写未量化的形容词、不用比实际更强的说法。**

## 2. 存储：路径 / 数据结构 / 增量全量 / 清理

### 2.1 路径：清单跟检查点走，**对象库全局共享**（决议 5）

```
data/snapshots/objects/{sha[:2]}/{sha}.bin   # ← M9-8 新增。**全局一份，项目级共享**
                                             #    跨会话、跨工作区里的所有会话去重

data/checkpoints/{session_id}/          # 已存在（agent/session.py:91-92 `_checkpoints_root`）
├── step-1.json                         # 对话检查点（现有格式，一字不改）
├── step-5.json
├── step-10.json
└── ws/                                 # ← M9-8 新增
    ├── step-1.json                     # 每一步一份的清单（**只搬清单，不搬对象**）
    ├── step-5.json
    └── step-10.json
```

**为什么清单放在检查点目录里，而不是工作区的 `.codeagent/`：**

1. **同一个坐标系是这一项的全部意义**。`--rewind --step K` 与 `--fork --step K`
   必须指同一个 K，否则"回到第 K 步"这句话有两个含义。放在同一目录下，
   这个一致性是**结构性的**，不靠约定。
2. **`.codeagent/` 在工作区内 = 会被自己快照进自己**（`TASKS.md` 的 M9-8 条目「要老实回答的难点」第 ② 点已点出这个坑）。
   放进 `data/` 也不够——`data/` 同样在工作区内（`data/*` 已在 `.gitignore`）。
   真正的隔离来自**登记只发生在 `write`/`edit` 上**：快照自己写对象库走的是直接
   `Path.write_text`，**不经过门禁链**，所以永远不会登记自己。这一点要写进代码注释。
3. **清单的清理粒度天然是会话级的**：`data/checkpoints/{sid}/ws/` 整个删掉即可。

**对象库为什么**（决议 5，理由与本文档初稿相反，见 §10 决议 5）：初稿倾向
per-session（"简单、可整目录删"），代价是 **fork 必须复制全部对象**。E 动线实测
（§8）给出的事实是：fork 之后对象库增量 **0 个对象 / 0 字节**，而清单增量
**+600 字节** —— 也就是说"共享"买到的是**整个对象库**，"不共享"要付的也是
**整个对象库**。per-session 在"倒带重试"这个主用法上（fork 与 rewind 成对出现）
会让每次重试都复制一遍当时的工作区。

**代价（如实记）**：两个新问题，都已有对应的处理：
- **回收不能按会话整目录删**（别的会话可能还引用同一批对象）→ 已实现为
  `drop_snapshots()`：先删清单，再从**所有剩余清单现算** live set，删掉 `used - live`。
  **不存引用计数** —— 存计数就是第二个真相源，不一致的表现是"某个会话的回滚悄悄失效"。
- **并发写同一个对象**（两个进程/两个工作区）→ 原子替换 + 容忍"替换失败但目标已在"。
  **不加锁**，实测依据见 §8 的 E 动线。

### 2.2 数据结构

**对象库**：`data/snapshots/objects/{sha256[:2]}/{sha256}.bin` —— 文件内容的原样字节，
按内容哈希命名。同内容只存一份（**天然去重，跨步骤、跨文件、跨会话都成立**）。

**清单 `ws/step-K.json`**（**全量**：记载"到第 K 步为止，我们管过的每一个路径，
在第 K 步时的状态"）：

```json
{
  "schema": 1,
  "session_id": "s20260912-101530",
  "step": 10,
  "ts": 1757654321.5,
  "files": {
    "textstat.py": {
      "sha256": "ab12…", "size": 2145,
      "base": {"existed": true, "sha256": "ffff…", "size": 1903}
    },
    "tests/test_textstat.py": { "sha256": "cd34…", "size": 880 },
    "notes.md": {
      "sha256": "ee56…", "size": 12,
      "base": {"existed": false}
    }
  }
}
```

三条不显然但必要的约定：

- **`base` 只在路径首次出现在清单里的那一步记一次**。它是"**我们碰它之前**它长什么样"，
  用来支持"回滚到第一次修改之前"。没有它，`--rewind --step 5`（而某文件第一次被改
  是在第 7 步）只能**删掉**这个文件 —— 而它可能是仓库里本来就有的、人写的文件。
  **那是一次静默的数据破坏**，正是本项目最不能接受的一类失败。
- **`base.existed == false`** 表示"我们碰它之前它不存在" → 回滚到那之前 = **删除**。
  这是与"内容为空"完全不同的两件事，必须分开记。
- **清单里没有 `existed` 字段**：路径在清单里就意味着"第 K 步时它归我们管且存在"
  （我们的工具只能创建/改写，不能删除）。**"不在清单里"的含义由 §2.5 的算法定义。**

**不变式（要在代码里 `assert`，并各配一条测试）：**

> **`path ∈ manifest[K]` ⟺ `first_touch(path) ≤ K`**

以及由"清单全量"推出的：

> 若 `K ≥ first_touch(path)`，则 `path ∈ manifest[K]`（不需要往前翻任何清单）

### 2.3 增量/全量：**清单全量 + 对象增量**

这是被显式问到的那个选择，所以把三个候选逐条摆出来：

| 方案 | 还原是否需要重放 | 中间丢失一环 | 未变文件的开销 | 完整性校验 |
|---|---|---|---|---|
| **A. 存每次编辑的前像**（移植版的做法，`session.py:998`） | 需要（按序反向重放） | **还原不出来** | 无 | 无 |
| **B. 每步全量复制所有受管文件** | 不需要 | 无影响 | **每步都付** | 无 |
| **C.（采用）清单全量 + 对象增量** | 不需要 | 无影响 | **0**（对象已存在，清单里复用哈希） | 哈希可校验 |

**采用 C。** 三条理由：

1. **每一步都能独立还原**（清单是全量的，不依赖任何别的清单）。A 的失败方式是
   本项目最怕的那种：删掉中间一步，后面的还原**静默出错**。
2. **"增量"落在对象层**：只有内容真变了才写新对象。覆盖了 B 的痛点，
   又不需要为"没变的文件"付任何代价。
3. **哈希顺带给了完整性**：对象被截断/手改 → 还原前校验失败 → **如实报错**，
   而不是把一段损坏内容写回工作区。对一个以"不静默丢失"为主线的项目，
   这个属性值钱。

**为什么不压缩**：`zlib` 会省空间，但会引入"压缩后哈希 ≠ 内容哈希"的二级账
（要么哈希压缩后的字节 → 无法与盘上内容比对；要么解压后再比 → 每次读都要解压）。
**在测出真实占用之前不引入这一层**。§8 的真跑里要**实测对象库占用**，
用数据决定要不要加。

### 2.4 写盘顺序：**引用必须在被引用者之后写**

`Session.checkpoint(state)` 里按这个顺序（不是可以随便挑的顺序）：

```
1. 写对象   ws/objects/{sha}.bin          ← 被引用者
2. 写清单   ws/step-K.json                ← 引用者（引用 1）
3. 写检查点 step-K.json                   ← 引用者（引用 2，且是人读的"这一步存在"的凭据）
```

**理由**：任何一步被杀，留下的都必须只是"**孤儿**"（不可达的字节），
而不能是"**说谎的引用**"。反过来（先写 `step-K.json`）会造出
"检查点说第 K 步有快照、但快照不存在" —— 而这正是 `--rewind --step K` 会撞上的东西。

**连带的一个决定**：`--rewind --step K` 只认 `ws/step-K.json` 存在与否，
`step-K.json` 存在而 `ws/step-K.json` 不存在时**明确报"这一步没有工作区快照"**
并列出实际有快照的步（同 `_load_payload` 在 `agent/session.py:446-453` 的做法：
报错必须给出下一步，只说"找不到"等于把用户扔在原地）。
**M9-8 之前的检查点全部属于这种**（老会话没有 `ws/`）—— 这是必须覆盖的兼容路径。

**强制检查点也要快照**：`Session.checkpoint` 有四个调用点
（`agent/loop.py:462` 常规节拍、`:738` `await_user`、`:884` goal、`app/repl.py:778` `_wrap_up`），
**全部经由这一个方法**，所以把快照挂在 `Session.checkpoint` 内部，
**一个挂钩点覆盖四个调用点**。这既是本项目的结构偏好（一处实现，防止漂移），
也是正确性要求：如果只有常规节拍快照，`--rewind --step K` 对那些强制落盘的步会失败，
而失败原因完全无法从用户视角解释。

### 2.5 恢复算法（含"我们没碰过的文件不动"）

```
restore(K):
  manifests = {n: load(ws/step-n.json) for n in 所有有快照的步}
  lo        = min(manifests)          # 最早一个有快照的步

  if K ∈ manifests:      target = manifests[K]
  elif K < lo:           target = None     # ← 「那时什么都没受管」，见下
  else:                  报错并列出可用步   # 夹在两个快照中间的步（如 5 与 10 之间的 7）

  managed   = ⋃ m.files.keys()
  first     = {p: min{n : p ∈ manifests[n].files} for p in managed}

  plan = []
  for rel in sorted(managed):
      if target is not None and K >= first[rel]:
          want = target.files[rel].sha256          # 不变式保证一定在
      else:
          base = manifests[first[rel]].files[rel].base
          want = base.sha256 if base.existed else ABSENT

      if want is ABSENT:       now 存在 → ("delete", rel)
      elif now 不存在:          ("restore", rel, want)
      elif hash(now) != want:  ("restore", rel, want)
      else:                    ("same", rel)          # 报告里单列，不算改动

  逐条执行；每条的结果（成功/失败+原因）都进报告
  未变的文件、以及不 ∈ managed 的文件：**一个都不动**
```

**`K < lo` 这一支是必须单独有的，不是"顺手兼容"**（M9-8 实现期补上的）：

- `min(manifests)` 就是**第一个有受管文件的步**。比它还早的 K 意味着"那时我们
  一个文件都没管过" —— 这是**事实**，不是猜测。于是所有受管路径都回到各自的 `base`。
- **没有这一支，`base` 是不可达的**：任何 `K ≥ lo` 且 K 是快照步的情况下，
  `K ≥ first[rel]` 恒成立，`else` 分支永远走不到 —— 那么 `base` 这套结构就是
  **写了没人用**的东西，而"回滚到第一次修改之前"这句话也就没有出口。
  `--rewind --step 0`（"撤销我们做过的一切"）走的正是它。
- 它与**夹在两快照之间的步仍然报错**并不矛盾：第 7 步是"第 5 步之后、第 10 步之前"，
  我们**确实**在第 7 步管过文件，只是没有那一步的盘面记录 —— 那是"不知道"，
  必须报错；而"早于第 5 步"是"那时没有"，是知道的。**这两件事不能混。**

**"不在 managed 里的文件一个都不动"这条是有意的，也必须说出来**：
它同时是**安全属性**（不会误删人写的文件、不会被 `bash` 建的文件迷惑）
和**能力边界**（`bash` 建/删的文件不在回滚范围内，见 §1.2）。
§1.3 的 M3 应对就是把这个数字报出来。

**恢复是逐文件的，不是原子的**：中途失败（权限错误、文件被占用）要如实报
"恢复了 3/5，第 4 个失败：<原因>"。**不假装清干净了**（同 `settle()` 在
`agent/subagents.py:465-469` 的取向：宁可如实报，也不假装）。

### 2.6 清理陈旧快照

**结论：M9-8 不引入任何自动清理机制。** 三条理由，逐条对应一个已存在的做法：

1. **快照与检查点同生命周期** —— 现在检查点**没有**保留策略（`data/` 下全留），
   所以快照也不需要独立的清理策略。清理检查点就是清理快照，粒度天然一致。
2. **一个会自动删用户数据的机制，在没有真实需求之前不该存在。**
   同 `settle()` 的有界 join：宁可如实报"还有东西没清干净"，也不假装清干净了。
   自动 GC 的失败方式是**删掉还能救回来的东西**，而这个项目的用户就是靠回滚救命的。
3. **但"占用不可见"是不可接受的** —— 那会让人在磁盘满的时候才发现。
   所以提供**只读的可见性出口**（见 §5 的 `--snapshots`）：
   - 每一步的步号、受管文件数、该步清单大小
   - 对象库总占用、对象数
   - **孤儿对象数**（对象库里没有任何清单引用到的对象）

**孤儿对象是真实存在的**，来自 §2.4 的写盘顺序（写完对象、还没写清单就被杀）。
**如实报告，不自动删** —— 这也是 `--snapshots` 要打这个数字的原因：
可见但不擅自动手。

**明确不做（理由留痕）**：
- **`--gc` / 自动清理孤儿对象** —— 见上第 2 条。将来若真要做，判据是"对象数与
  引用数的差值持续增大"，而不是"看着碍眼"。
- **检查点保留策略（`--keep-last N`）** —— 超出 M9-8 范围，且它是**破坏性**的，
  值得单独一个里程碑 + 单独的 review，不该混在 rewind 里悄悄带进来。

### 2.7 明确不做的存储设计（理由留痕）

- **增量 diff 链**（存 `old→new` 的 patch）：还原变成"按序重放"，
  任何一环缺失就**静默还原出错**。见 §2.3 的 A 方案。
- **压缩**（zlib/zip）：见 §2.3 末尾 —— **先测，再决定**。
- **跨会话的引用计数**：初稿把"共享对象库"整个列为不做，理由是"引用计数 =
  两个真相源"。**共享本身已被决议 5 采纳**（§2.1），但那条理由仍然成立并被遵守：
  活跃集是**从所有剩余清单现算**的（`_live_shas`），**不存计数**。
  被否掉的是"存计数"，不是"共享"。
- **`ws/objects/` 按会话隔离**：初稿的选择，E 动线实测后被决议 5 推翻（§10 决议 5）。
- **内容寻址的对象名加盐 / 混淆**：没有必要。快照内容就是工作区文件内容，
  它本来就在工作区里躺着，哈希不泄漏比文件本身更多的东西。

## 3. 与 Subagent 的交互协议

### 3.1 现状：worker **结构上**写不了文件

已核实（`agent/tools/subagent.py:71-75`）：

```python
_READ_ONLY_TOOLS = {"glob": GlobTool, "grep": GrepTool, "read": ReadTool}
```

`_restricted_registry`（`agent/tools/subagent.py:146-156`）**只从这个白名单里取**，
所以 worker 拿不到 `write` / `edit` / `bash` / 任何子代理工具。**白名单而不是黑名单**
（模块 docstring 第 8 行明写："黑名单在'以后加了新工具'时会静默失效"）。

**所以"子代理的变更如何合并"这个问题，在当前代码下是空的 —— 没有变更可以合并。**

但"当前是空的"不等于"不需要协议"。下面两条是这一节真正的产出。

### 3.2 结构性防线：**快照挂在 `Session` 上，不挂在引擎上**

这是本项与 subagent 交互的**唯一核心决定**，而且它是一条**免费**的防线：

```
Session (owner of workspace_root, data/ 目录)
  └── self.snapshots: WorkspaceSnapshots      ← M9-8 新增
        ├── note_write(path, before)          ← 引擎在门禁链成功后调用
        ├── capture(step)                     ← Session.checkpoint 内部调用
        └── restore(step)                     ← CLI/REPL 调用
```

**worker 的 `QueryEngine` 拿不到 `Session`** —— 这是 M9-7 已经定下的隔离
（`agent/tools/subagent.py:196-210`，注释里明写「刻意**不给**的四样」，
第一条就是 `session`，理由是 `Session.checkpoint` 没有锁，两个 worker 同 session_id
会互相覆盖检查点文件）。

于是：**worker 结构上无法登记快照，也结构上无法触发快照落盘** ——
不是靠"我们记得不要给它"，而是靠"它没有那个对象"。
**一条已有的隔离机制同时覆盖了两件事**，不需要为快照再造第二套守卫。

这是对 `TASKS.md` 的 M9-8 条目「要老实回答的难点」第 ③ 点（"worker 的写操作在 M9-7 之后不存在，
所以快照不必跨线程"）的实现层回答：**不仅不必跨线程，而且跨线程在结构上不可能。**
也因此 §2.2 的清单/对象都**不需要任何锁**（只有父线程会写）。

### 3.3 一条断言钉住前提

结构防线锁住的是"**worker 拿不到 session**"。但白名单本身是可以被改的 ——
哪天有人往 `_READ_ONLY_TOOLS` 里加一个 `edit`，或者给 worker 引擎接上 `session`，
**rewind 会静默漏掉 worker 写过的文件**。这是本项目头号缺陷类的完美复现形状：
机制在、测试绿、没人接线。

**所以两条测试要钉住这个前提**（不是钉行为，是钉**前提本身**）：

```python
def test_subagent_tool_whitelist_is_read_only_only():
    """子代理工具白名单恰好是这三件，且全部 is_read_only()。

    这条断言的存在意义**不是**"白名单是这样"，而是让"往里加一个写工具"
    这个决定**必须显式改一条测试** —— 于是一个静默的决定变成响的决定。
    改它的同时必须重新审 M9-8 的 rewind 契约（见 docs/design/m9-8_rewind.md §3）。
    """

def test_worker_engine_gets_no_session():
    """worker 的 QueryEngine 构造参数里 session is None（同 permissions/hooks）。"""
```

**这两条测试的设计意图要写进测试的 docstring** —— 否则将来有人看到红，
第一反应是"改断言让它过"，而不是"哦，我得重新想 rewind"。

### 3.4 如果将来白名单真的松了

**不做**（理由留痕）：不预先实现"worker 写操作的合并协议"。
一个没有调用方的协议就是死代码，而它还会让读的人以为这件事已经处理过了 ——
比不写更糟。真到那一天，按 §3.2 的结论，正确的动作是
**让 worker 也通过父 Session 登记**（而不是各写各的清单），
那是一次显式的改动，届时按那个设计写。

### 3.5 与 `settle()` / 取消的交互

**没有交互，这也是设计的一部分。**

- 快照只在 `Session.checkpoint` 里落盘，**不在** `settle()` 的 `finally` 里
  （`agent/loop.py:478-486`）。`settle()` 可能跑在 `KeyboardInterrupt` 的传播路径上，
  在那里做文件 IO 是给一个可能正在抛异常的收尾路径加负担。
- 被 `close_agent` 叫停的 worker（`agent/subagents.py:429-452`）**没有写过任何文件**，
  所以"叫停"对快照没有任何影响。
- `abort`（`agent/loop.py:382`）命中的那个 `_aborted_result` 返回路径
  **不落检查点**，也**不落快照** —— 与它保持一致，不额外多一处写盘。

## 4. 与既有机制的交互

### 4.1 `fork()` 必须搬快照 —— 契约从"三样"变"四样"

`Session.fork` 现在搬三样（`agent/session.py:479-485`）：检查点 `step-1..K`、
轨迹里 `step ≤ K` 的行、meta 里的 `forked_from`。

**M9-8 加第四样：`ws/` 目录**。不搬的话，分叉出来的会话
`--fork --step K` 之后 `--rewind --step K` 会报"这一步没有工作区快照" ——
**而"两个坐标一起回到第 K 步"正是 M9-8 最有用的形态**（§1.3 M2 的应对 ③）。
不搬，那个形态就不成立。

做法（**实现与初稿不同，见决议 5**）：**只复制 `ws/step-n.json`（n ≤ K），
一个对象都不复制**。对象库是项目级共享的（§2.1），清单里的 sha 在原库仍然可读。
初稿写的是"复制而非硬链接"，那是 per-session 对象库下的做法；对象库改全局之后
**复制这件事整个消失了**。

**如实记代价**（§8 D 动线实测）：fork 的磁盘开销 = **新写的清单字节**，
对象增量 **0**。数字见 §8。

**顺带一条必须处理的**：`--fork --step K` 只复制 `n ≤ K` 的清单。
分叉点**之后**的清单不搬 —— 那是源会话的"未来"，不是分叉会话的经历。
不搬带来的直接后果是分叉会话的 `plan()` 看到的最早/最晚快照与源会话不同，
**这是对的**：分叉会话在回滚这件事上就该只知道自己走过的那一段。

### 4.2 `--resume` 的补投（见 §1.3 M2 的应对 ②）

新增 `_reinject_rewind`，与 `_reinject_plan`（`app/cli.py:495`）、
`_reinject_goal`（`app/cli.py:514`）**并排放在一起**（同一处 = 同一份实现，
单发与 REPL 共用）。

触发条件（再强调一次，这是全文最容易被做成"每轮都贴"的地方）：
**从检查点读出的步号 > 最近一次回滚的目标步**。

数据来源：轨迹里的 `workspace_rewound` 事件（append-only，一定写得进去）。
**读轨迹而不是读 state** —— state 是"任务跑到哪了"，而回滚是**发生在某个检查点之后
的一次人的动作**，它天然不属于那个检查点。这与 `forked_from` 放 meta 的理由同源
（`agent/session.py:16-20`：它是"派生自事件/人的行为的事实"，不是 AgentState 的字段）。

### 4.3 REPL 的 `/rewind`

- 加进 `_COMMANDS`（`app/repl.py:80`）。**`/help` 的正文由这张表生成**，
  所以加一个键 = 帮助里自动出现，不会漂移。有一条测试钉着键集合（已同步到 11 个）。
- **默认预览**，用 REPL 自己的 `_confirm_rewind`（**不是** `_yes_no_prompt`）——
  两者都用 `input()`，但常驻模式里默认那个 `typer.prompt` 会把 Ctrl+C 走成
  `Abort`，于是"我不想回滚"和"我想退出 REPL"分不开。**读不到明确同意（EOF / Ctrl+C）
  一律按取消**。这与 `--review-edits` 的交互形状一致，不新造一套。
- **`arg` 不是整数时直接返回，不当 0 用**：0 在这里是有真实含义的坐标
  （"撤销我们做过的一切"，走 §2.5 的 `K < lo` 那一支），把一个打错的字静默当成它，
  等于把用户的工作区一次抹干净。变异测试实测：把 `return` 改成 `step = 0`
  会被 `test_rewind_rejects_a_non_numeric_step` 抓住。
- 回滚成功后**往当前会话就地追加说明**（`_reinject_rewind`，与 `--resume` 那条路
  **共用同一份实现**）。REPL 里人是**在一段活着的对话中途**回滚的，模型下一秒
  就要开口，它手上那份"我刚改过 X"的记忆已经作废 —— 只写 meta（那是 `--resume`
  才生效的路）在 REPL 里等于没说。

### 4.4 不进 `ToolRegistry.default()`

**没有 `rewind` 工具，模型不能自己回滚。** 与 `ask_user` / goal 工具同一条判据，
外加一条更硬的：**回滚是"人对自己工作区的操作"，它是破坏性的**。
让模型能自己调 `rewind` = 给它一个撤销自己错误的机会，也 = 给它一个
**销毁证据**的机会（把改坏的文件恢复原样，然后说"我没改过"）。
判分权在人手里 —— 与 M9-6 `declare_goal_done`（刻意不叫 `complete_goal`）、
M7 `clear_taint`（只有人能清）是**同一条纪律**。

## 5. 命令面

| 命令 | 语义 | 需要 key |
|---|---|---|
| `--snapshots` | 只列：所有有快照的会话、每一步、清单大小、对象库占用、孤儿对象数 | **否** |
| `--drop-snapshots --session-id S` | 删掉一个会话的快照清单，回收**不再被任何会话引用**的对象 | **否** |
| `--rewind [--session-id S] [--step K]` | **预览**（不写盘）：恢复/删除/未变/不在管辖范围 四栏 + bash 调用计数 + 不回滚什么；然后**问一次确认** | **否** |
| `--rewind … --force` | 跳过确认，直接执行 | **否** |
| REPL `/rewind [K]` | 预览 → `_confirm_rewind`（默认 **n**）→ 执行 | 否（在 REPL 里） |

**全部不需要 API key，也不建引擎、不跑任务** —— 与 `--plan`（`app/cli.py:609`）、
`--goal` 同一条路径：**快照是磁盘上的事实，读它就够了**。
这与 `--agents` 恰好相反（`TASKS.md` 的 M9-7 条目：worker 是进程内瞬时的，
盘上什么都没有），那个对比值得写进注释。

**`--step` 省略 = 最近一个有快照的步**（**不是**最近检查点 —— 老会话有检查点没快照，
回落要不就报错、要不就用有快照的那个，见 §2.4）。

**默认先预览、再确认，`--force` 才跳过**（决议 2，与初稿的 `--apply` 相反）：
初稿给的是"显式开关才执行"，方向对，但**开关的默认一侧仍然危险** ——
`--rewind` 一旦被当成"看一眼"的命令敲出去，装上 `--apply` 与否只差一个词的记忆。
决议 2 把它改成**两段式**：预览永远先出，确认框的默认值是 **n**。
理由不是保守，是这件事的性质：**回滚是全项目唯一一个会覆盖和删除用户文件的操作**，
对象库留了旧字节，但被覆盖的文件本身没有 undo。
它与 `--fork`（无确认）风格不一致，这是**刻意的**：分叉只写新的会话目录，
不碰用户已有的任何字节。

**执行完之后要说清出口**：打印 `--resume --step K`（K 是 `plan()` 解析出来的目标步，
不是用户敲的那个数 —— `--step` 省略时两者不同）。只说"已回滚"而不给下一步，
等于让人对着一个回到过去的文件系统、一段停在最新一步的对话干活 ——
那正是 §1.3 M2 描述的那种错位。

**输出示例（真实运行的输出，`m9verify/drive_m9_8_c_rewind.log`）：**

```
回滚预览: s20260912-021118 的工作区 → 第 1 步
  - 删除  draft.md （378 B → 删除）
  ~ 还原  pkg/alpha.py （2012 B → 1949 B）

  不受影响: 0 个文件（它们在这段里没变过）
  不在管辖范围: 3 个文件（从没被 write/edit 碰过，回滚**不动**它们）
  ⚠ 不会被回滚的副作用: 1 次 bash 调用 + 0 次其它工具调用
────────────────────────────────────────────────────────────────────
确认把上面这 2 个文件回滚到第 1 步？（这会覆盖/删除磁盘上的文件，不可撤销；加 --force 可跳过此问）
工作区已回滚到第 1 步: 2 个文件处理完成
  继续: python -m app.cli --resume --session-id s20260912-021118 --step 1 "你的指示"
```

"不在管辖范围"那一栏的**口径写死为**：工作区里没被 `write`/`edit` 碰过的普通文件数，
跳过 `data/` 与 `.git/`（`_excluded` + `_count_outside`）。
口径含糊的计数比不报还糟 —— 所以它和"回滚动不了的 bash 调用数"是**两个分开的数**，
不合并（决议 6）。

1. **基座成本 = 被 `write`/`edit` 碰过的那些文件的原始字节之和，不是整个工作区。**

   所以不需要开关。
2. **清单比对象小一个量级**（599 B vs 4339 B ≈ **13.8%**）。每步全量清单的代价是
   真实但可控的；而它买到的是"每一步都能独立还原"（§2.3）。
3. **孤儿对象实测 0 个**。写盘顺序（对象→清单→检查点）在正常路径上不留孤儿；
   孤儿只在"写到一半被杀"时产生，报告里如实列出、不自动删（§2.6）。

| 项 | 实测 |
|---|---|

**决议 7 —— 对象库要不要加锁？**

`m9verify/drive_m9_8.py e_disk` 里的探针：**8 线程 × 5 轮 = 40 次写入，
全部抢同一个 sha 的目标名**（最坏情况）。分两段量：

| 段 | 实测 |
|---|---|
| ① 裸替换（`tmp.replace(target)`，不经任何容错） | **冲突 24~30 次 / 40 次**，全部是 `PermissionError`（6 次独立重跑：30 / 25 / 27 / 24 / 28 / 26） |
| ② 经 `_put_object` | **未捕获异常 0 次**（每次重跑都是 0） |

**结论**：冲突在 Windows/NTFS 上是**真实且高频**的（一半以上的写入会撞），
但它**已经被容错完全覆盖** —— 内容寻址下同一个 sha 就是同一份字节，谁赢都一样，
所以"替换失败但目标已在"是成功，不是失败。**加锁是在排除一个已经不存在的问题**，
而锁的代价（粒度、跨进程锁放哪、死锁）是真的。→ **不加锁**（决议 7）。

**这个结论有一半是"如实标注"**：① 的失败率在 Linux 上通常为 0（`rename(2)` 是
原子的且不抛 `EACCES`），所以**那条容错分支在别的平台上可能是死代码** ——
但它不是"为了保险加的"，是这台机器上实测出来的。两个平台都不需要锁。

## 9. 明确不做（理由留痕）

| 不做 | 理由 |
|---|---|
| **模型可调用的 `rewind` 工具** | §4.4：回滚是破坏性的、且是"人对自己工作区"的操作；给模型 = 给它销毁证据的能力 |
| **自动 GC / 自动清理陈旧快照** | §2.6：会自动删用户数据的机制，在没有真实需求前不该存在 |
| **检查点保留策略（`--keep-last N`）** | §2.6：破坏性、且是独立的一件事，值得单独 review，不混在 rewind 里带进来 |
| **快照压缩** | §2.3：E 动线实测对象库只有 4339 B（一个 8892 B 的工作区），
**没有任何压缩的动机**；压缩还会引入"压缩后哈希 ≠ 内容哈希"的二级账 |
| **增量 diff 链** | §2.3：还原需要重放，中间缺一环就静默出错 |
| **跨会话的引用计数** | §2.7：被否的是"存计数"，不是"共享"（共享已按决议 5 采用）。
活跃集从所有剩余清单**现算** |
| **git 集成（撤销 commit / `git stash` 联动）** | 越界。且 `git` 状态本来就明确列为"不回滚"（§1.2），做一半比不做更误导 |
| **跨工作区回滚 / 回滚别的会话改过的文件** | 文件系统没有"谁改的"这个概念，做不到；别声称 |
| **worker 写操作的合并协议** | §3.4：没有调用方的协议就是死代码，且会让读的人以为这件事处理过了 |
| **`--sessions` 表格里显示快照占用** | 那张表的用途是"找回一个会话"，加一列体积会挤掉血统信息；占用去 `--snapshots` 看（§5） |

## 10. 六条开放问题的**决议**（逐条给出拍板结果）

> 这一节从"待拍板"改成"决议"：六条全部有了结论，**每条的结论都指向本文档里已被
> 改写的那一节**。初稿的提问原文原样保留在下面 —— 它与结论的差值是这份文档最有
> 信息量的部分（尤其是第 1、5 条：**两条都因为 E 动线的实测数字而加强或反转**）。

### 决议 1 · `base` 的磁盘代价 → **直接存，不加开关**

**实测把这个问题问错了**：初稿假设"受管路径 ≈ 工作区里的文件"。E 动线实测：
工作区 5 个文件 / 8892 B，**进清单的只有 2 个**（被 `write`/`edit` 碰过的那两个），
基座 **1949 B**。**代价的上界是"这次任务改动的体量"，不是"仓库的体量"**（§8）。

- **不加开关。** 初稿那句"一个能关掉正确性的开关，迟早会有人在不知道后果的情况下
  关掉它"在实测之后更成立 —— 现在还能补上具体数字：它省下的是**改动体量**级别的
  空间（100 MB 仓库里改一个 2 KB 文件 = 省 2 KB），赔上的是"回滚到第一次修改之前
  会删掉人写的文件"。
- 补救出口仍然是 `--drop-snapshots`（会话级，人显式敲）。**不做自动 GC**（§2.6）。

### 决议 2 · 默认行为 → **两段式：先预览，再确认；`--force` 跳过**（不是 `--apply`）

初稿的 `--rewind --apply` 方向是对的（破坏性动作要显式），但**开关的默认一侧仍然
危险**：`--rewind` 被当成"看一眼"敲出去时，装不装 `--apply` 只差一个词的记忆。
决议改成预览永远先出、确认框默认 **n**（§5）。

- **与 `--fork` 无确认的风格不一致是刻意的**：分叉只写新的会话目录，不碰用户已有的
  字节；回滚是全项目唯一一个**会覆盖和删除用户文件**的操作。
- **读不到明确同意（EOF / Ctrl+C）按取消**；REPL 里用 `_confirm_rewind` 而不是
  默认的 `typer.prompt`（否则 Ctrl+C 的语义会和"退出 REPL"混起来）。

### 决议 3 · `--fork --step K --rewind` → **做，且回滚必须在"只分叉不续跑"那个 `Exit` 之前**

它是 P1 需求：单用 `--fork` 会造出"对话在第 K 步、文件在最新一步"的错位，
而那正是 M9-5 B 动线里模型说"我已经修好了"却什么都看不到的成因。
落点是一个**顺序**问题，所以 §8 动线 D 刻意走 CLI 子进程验收 ——
直接调函数会绕过它，而那正是本项目的头号缺陷类。

### 决议 4 · `_reinject_rewind` 的触发条件 → **精确判据**

判据是**状态机式**的，不是保守式的：`恢复步号 > 回滚目标步` 才补投，
且回滚成功后写 meta 的 `last_rewind`（§4.2）。保守判据（"有回滚记录就补投"）
会在 `--fork --step K --rewind` + `--resume --step K`（本来就同坐标）时多说一句话 ——
而"多说一句无意义的话"正是让人开始忽略这类通知的第一步。

### 决议 5 · 对象库隔离粒度 → **全局共享**（初稿的倾向被实测推翻）

**初稿倾向 per-session，理由是"简单、可整目录删"。E 动线把这个理由拆掉了**：

| | per-session（初稿） | 全局共享（决议） |
|---|---|---|
| fork 的磁盘增量 | **复制整个对象库** | **0 字节对象 + 599 字节清单** |
| 回收 | 整目录删 | 从所有剩余清单**现算** live set，删 `used - live` |
| 并发写 | 单进程内无 | 原子替换 + 容忍"失败但目标已在"（**不加锁**，实测见 §8） |

"倒带重试"这个主用法是 **fork 与 rewind 成对出现**的，所以 per-session 的代价
不是偶发的一次复制，而是**每次重试都复制一遍当时的工作区**。
**"引用计数 = 两个真相源"那条反对意见仍然成立并被遵守** —— 被否的是"存计数"，
不是"共享"（§2.7）。回收实测：删源会话清单 → 回收 1 个对象 / 746 B，
另 3 个因别的会话还在引用而保留（§8 动线 F）。

**连带改动**（初稿没有的）：
- `data/snapshots/objects/` 取代 `data/checkpoints/{sid}/ws/objects/`（§2.1）；
- `fork` 从"按引用复制对象"变成"只复制清单"（§4.1）；
- 新增 `--drop-snapshots` 这个出口（§5）—— 没有它，"共享"就变成了"永远删不掉"。

### 决议 6 · "不在管辖范围"的计数口径 → **保留，且拆成独立维度**

口径写死为"工作区里没被 `write`/`edit` 碰过的普通文件数"，跳过 `data/` 与 `.git/`。
**更关键的是不能把它和别的数混起来**：预览里四个数**分开打**（§8 动线 C）——
文件系统回滚 / 不在管辖范围的文件 / 回滚不了的 bash 调用 / 其余可能有副作用的调用。
把后两个揉进前两个、或者给一个"影响范围"的平均值，等于**把"回滚动不了外部副作用"
这件事用另一个数字盖过去** —— 那是推卸责任，不是如实报告。

### 附加决议 7 · 对象库加锁 → **不加，实测说话**

用户裁定：「在获得真实数据之前绝对不要硬编码任何关于磁盘的数字」、
「不要凭空增加锁的复杂度」。E 动线的探针就是这件事的实测（§8 决议 7）：
裸替换 40 次里冲突 24~30 次（真实且高频），经 `_put_object` **未捕获异常 0 次**
（容错完全覆盖）→ **不加锁**。容错不是"为了保险加的"，是这台机器上实测出来的。

**同时如实标注**：这条结论依赖文件系统 —— Linux 上 `rename(2)` 通常不抛 `EACCES`，
那条容错分支在别的平台上可能是死代码。**两个平台都不需要锁。**

### 初稿的提问原文（保留，供对照）

1. **`base` 的磁盘代价能不能接受？** 每个受管路径要多存**一份它被改之前的内容**，
   永不回收（§2.2）。不存的话，"回滚到第一次修改之前"就只能**删掉那个文件** ——
   而它可能是仓库里本来就有的、人写的文件。**我倾向存**，但这是本项最大的单笔磁盘开销，
   且要等 E 动线测出真实数字。**要不要先用一个开关关掉它？**（我倾向不要 ——
   一个能关掉正确性的开关，迟早会有人在不知道后果的情况下关掉它。）

2. **`--rewind` 默认预览、`--apply` 才动手** —— 还是反过来（`--rewind` 直接执行、
   `--dry-run` 预览）？我倾向第一种（破坏性动作用显式开关），
   但它与 `--fork`（无确认、直接执行）的风格不一致，需要拍板。

3. **`--fork --step K --rewind` 这个组合入口要不要做？**
   我倾向要（§1.3 M2 应对 ③，它是本项最有价值的形态），
   但它是"一条命令里同时动两种状态"，值得单独确认。

4. **`_reinject_rewind` 的触发条件** —— 我给的判据是"resume 步号 > 回滚目标步"（§4.2）。
   更保守的替代是"只要这个会话有回滚记录就补投"：永远不会漏，但会在
   `--fork --step K --rewind` + `--resume --step K`（本来就同坐标）时多说一句话。
   **我倾向精确判据**，但精确判据多一处可能出错的比较。

5. **对象库的隔离粒度** —— per-session（§2.1，简单、可整目录删）还是全局共享
   （§2.7，省 fork 的复制开销、但要引用计数）？**我倾向 per-session，用 E 动线的
   数字再复核一次**。如果 fork 的复制代价实测很大（比如单次 fork 几十 MB），
   这个决定要重开。

6. **"不在管辖范围"那一栏的计数口径**（§5）—— 我提议"工作区顶层、不含 `data/` 与 `.git/`
   的普通文件数"。这个口径要不要更保守（比如干脆不报这个数，只报 bash 调用次数）？

## 附：与三份参照的关系（一句话各自）

- **TS 原版 `F:\MiniCode-main`**：`src/` 下 `rewind` **零命中** —— 本项**不对齐原版**，
  是移植版独有的能力。

  **不取它的形态**（§2.3 的 A 方案）—— 同 M9-2 对 `_is_safe_url` 的做法：
  **照意图重写，不照抄。**

  挂在**同一个 K** 上，两者合起来才是"回到第 K 步"的完整含义。
